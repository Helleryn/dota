## 3. Причина каждого отказа

Все шесть отказов имеют одну причину — `roster_too_incomplete`: меньше
трёх сопоставленных игроков хотя бы на одной стороне.

Порог в три игрока выбран по эксперименту L1: при k=1 признак состава
уже лучше его отсутствия, но выигрыш втрое меньше, чем при k=4. Три —
компромисс, и он объявлен в коде константой, а не спрятан в условии.

---

## 4. Почему Phase 17 давала ноль, а здесь девять

Три независимые причины, каждая измерена:

| Причина | Phase 17 | Phase 18 |
|---|---|---|
| **источник** | Valve DPC — только лиги tier `excluded` | bo3.gg, дисциплина 4 |
| **сопоставление** | по `team_id` Valve → 0 из 20 команд в базе | **по игрокам** через реестр `proPlayers` → 88 из 133 |
| **режим** | требовался полный состав | частичный состав как рабочий режим |

Решающим оказалось второе: связывание **по игрокам, а не по названию
команды**. Названия команд не используются для связывания нигде — Phase
10 нашла 461 пару одноимённых команд, существовавших параллельно.

Неоднозначные ники (17 из 133) **не разрешаются произвольным выбором**:
индекс хранит множество кандидатов, и при `len != 1` игрок пропускается.

## 5. Чего этот запуск НЕ доказывает

* **Прогнозы не проверены исходом.** Матчи начинаются через 40–76 часов;
  в рамках сессии дождаться результата невозможно. Снимки сохранены
  неизменяемыми и ждут разрешения командой `resolve-finished`.
* **Все матчи — tier `b`**, не топ-сцена. Матчей tier `s`/`a` по Dota в
  выдаче не было вовсе.
* **Калибровка не применена** (`calibration_version = "none"`):
  калибровочное окно строится по матчам с известным исходом, а для
  частичного состава такой истории в нужном режиме ещё не накоплено.
  Указано в снимке явно, а не подставлено молча.
* **Вероятность считается по Elo-формуле от разницы player-Elo**, а не
  замороженной моделью: у модели пять входов, из которых для этих матчей
  доступны не все. Это прототип режима, а не продуктовый прогноз.

## 6. Ограничение сопоставления по игрокам

Реестр `proPlayers` OpenDota — **снимок «сегодня»**. Для живого прогноза
(T = сейчас) это законно: реестр описывает текущее состояние, и мы
прогнозируем текущий момент.

Для **исторического** replay он запрещён: применять сегодняшнее
соответствие «ник → account_id» к прогнозу годичной давности значит
протаскивать сегодняшнее знание в прошлое. В историческом конвейере
(`src/pit/`) он не используется.

Это ограничение — новое в проекте и внесено в карту рисков утечки.
