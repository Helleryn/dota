# PHASE 15 — план: shadow validation и переход к прогнозам на будущее

> План зафиксирован **до** реализации. Phase 15 — **не** ML-фаза. Модель
> заморожена; ни один признак не добавляется и не меняется.

---

## 0. Что заморожено

**Модель** (`PHASE9_FULL`, пять входов — в документации именно пять):

```
elo_difference, form_3_difference,                          <- frozen baseline (Elo K=16, Form3)
elo_mean_diff, five_vs_team_elo_diff, hero_exp_decay_diff   <- KEEP Phase 9
```

Логистическая регрессия, `random_state=42`, SimpleImputer(constant 0.0) +
StandardScaler — как в Phase 9/12/13/14.

**Калибровка** (результат Phase 14): beta-калибровка на скользящем окне
5000 исторических матчей, пересчёт раз в 10 матчей.

Отдельно фиксируется решение Phase 14: **патч-локальная составляющая
гибрида в прод не берётся** — на VALIDATION она помогала, на TEST в трёх
окнах из четырёх сделала хуже. В shadow-режиме используется чистое
скользящее окно.

**Мера уверенности**: `|P_calibrated − 0.5|` (Phase 13: практически
исчерпывающая; новых мер не вводится).

## 1. Результат PART A — и почему он меняет форму фазы

Проверены реальные ответы API, а не предположения.

| Проверка | Результат |
|---|---|
| `/health` | **OK** |
| `/proMatches` | **OK**, свежайший матч 2026-08-25 21:19 UTC |
| `/live` | **OK**, 100 записей, **но league_id есть у 0 из них** |
| `/scheduledMatches`, `/upcomingMatches`, `/matches/upcoming`, `/schedule`, `/fixtures` | **HTTP 404 — таких эндпоинтов нет** |
| `/explorer`: матчей с `start_time` в будущем | **0** |
| `/explorer`: максимальный `start_time` в БД OpenDota | 1787692744 = 2026-08-25 |

> **У OpenDota нет расписания будущих матчей.** Ни одного эндпоинта с
> фикстурами не существует, и в её базе **ноль** матчей с будущим
> `start_time`: матч появляется только после того, как сыгран.

Из Phase 11 уже известно, что Liquipedia отдаёт HTTP 429 на первом же
запросе, а STRATZ — HTTP 403 без ключа. Скрейпинг не проводится.

**Следствие для фазы, названное прямо:** полноценная prospective
validation на анонсированных матчах **невозможна с имеющимися
источниками**. Это ограничение данных, а не решение отложить работу.

### Что при этом возможно

| Режим | Возможен? | Что даёт |
|---|---|---|
| **LIVE-DRAFT** — матч пойман в `/live` во время драфта (`game_time ≤ 0`) | **да, но не сейчас** | настоящий прогноз до исхода; в текущем срезе `/live` про-матчей нет вовсе |
| **REPLAY** — тот же код прогоняется по недавнему окну истории с искусственным «сейчас» | **да** | реальные live-метрики на том же коде, что и боевой путь |
| **FIXTURE** — прогноз по анонсу расписания | **нет** | источника не существует |

Фаза реализует все три пути; работают два, и каждый прогноз помечается
своим `source`, чтобы результаты никогда не смешивались.

## 2. Архитектура (PART B/E/Q)

```
DISCOVERED -> FEATURES_READY -> PREDICTED -> CALIBRATED -> PUBLISHED
                                                             |
                                        MATCH_STARTED -> MATCH_FINISHED -> RESOLVED
                                                             |
                                                          INVALID
```

Снимок прогноза **неизменяем**. Это не соглашение в коде, а инвариант
базы: триггер PostgreSQL разрешает у опубликованного снимка менять
**только** поле `state` и только вперёд по разрешённому порядку; любое
изменение вероятности, признаков, версий или отметок среза отклоняется
на уровне СУБД. Результат матча пишется в **отдельную** запись
разрешения и снимка не касается.

Версионирование: `model_version`, `feature_version`, `calibration_version`,
`prediction_version` — в каждом снимке.

## 3. Data cutoff (PART C) — центральная проверка

Для каждого прогноза сохраняются пять отметок:

| Поле | Смысл |
|---|---|
| `data_cutoff` | граница знаний системы в целом |
| `feature_data_cutoff` | самый поздний матч, вошедший в признаки |
| `rating_state_timestamp` | состояние Elo и player-Elo |
| `roster_state_timestamp` | состояние составов |
| `hero_meta_state_timestamp` | состояние статистики героев |

Автоматическая проверка **NO DATA AFTER prediction_timestamp**: любая из
пяти отметок позже времени прогноза ⇒ прогноз получает статус `INVALID`
с указанием причины. Не «предупреждение», а отказ.

---

## 4. Правило PART P — против p-hacking

После начала prospective validation **не меняются**: модель, признаки,
калибровка, пороги, Elo, форма, затухание героев.

При обнаружении дефекта: зафиксировать, определить затронутые прогнозы,
**не удалять их молча**, создать новую версию, продолжить. Старые
прогнозы остаются в базе со своей версией.

## 5. Обработка отказов (PART R)

Каждый случай получает статус, тихого fallback нет ни в одном:

| Ситуация | Статус |
|---|---|
| OpenDota недоступен | `INVALID: source_unavailable` |
| состав неизвестен | `INVALID: lineup_unknown` |
| матч отменён | `INVALID: match_cancelled` |
| матч перенесён | новый прогноз с новым `prediction_timestamp` |
| идентичность команды неоднозначна | `INVALID: ambiguous_team_identity` |
| патч неизвестен | `INVALID: patch_unknown` |
| истории для калибровки мало | `PREDICTED` без калибровки, `calibration_version = none` |
| данные противоречивы | `INVALID: inconsistent_data` |

## 6. Что будет и чего не будет доказано

**Будет:** воспроизводимость снимков, отсутствие данных из будущего,
корректность неизменяемости, работа калибровки на потоке, поведение
метрик по мере накопления выборки.

**Не будет:** утверждения «система проверена на настоящих будущих
матчах». Для этого нужен источник расписания, которого нет. Любые
live-метрики в отчётах помечены режимом (`REPLAY` / `LIVE-DRAFT`) и
никогда не складываются.

**Размеры выборки (PART O)** фиксируются заранее: выводы не делаются
раньше N=50; интервалы показываются на N ∈ {50, 100, 250, 500, всё
окно}. Ни один вывод не формулируется по первым 10–20 матчам.
