# LIVE DATA VERIFICATION

Дата проверки: 2026-08-24. Проверено прямыми запросами к `api.opendota.com`
(не через чтение исходников — в отличие от Phase 1) из этой сессии, сеть
открыта (см. раздел "Сравнение с Phase 1" ниже).

## 1. Доступность и статус API

| Проверка | Результат | Как проверено |
|---|---|---|
| `GET /api/proMatches` | HTTP 200, ~0.6с | `curl` |
| `GET /api/matches/{id}` | HTTP 200, 0.2-1.3с | `curl` на реальном match_id из `/proMatches` |
| `GET /api/explorer?sql=...` | HTTP 200, ~0.2-0.9с | произвольные SQL-запросы (см. ниже) |
| `GET /api/metadata` | HTTP 200 | `curl` |
| `GET /api/health` | **HTTP 500** | `curl` — см. примечание |

**Примечание про `/api/health`**: это НЕ признак блокировки сети — тело
ответа содержит реальные внутренние метрики инфраструктуры OpenDota
(`postgresUsage`, `redisUsage`, `cassandraUsage`, ...) с текущим `timestamp`,
т.е. запрос дошёл и обработан живым сервером; 500 — это, по-видимому,
собственная семантика эндпоинта (один из внутренних метриков превысил
`limit`), а не ошибка прокси/сети. Все содержательные эндпоинты (`/proMatches`,
`/matches/{id}`, `/explorer`, `/metadata`) отвечают 200 с корректным JSON.

## 2. Rate limits (подтверждено заголовками реальных ответов)

```
x-rate-limit-remaining-minute: 59   (из 60 — лимит 60/мин без ключа, VERIFIED)
x-rate-limit-remaining-day:    ~2989 -> ~2844 за сессию (из ~3000/день)
```

`/api/metadata` подтверждает те же цифры программно:
`freeRateLimit: 60`, `freeCallLimit: 3000`, `premRateLimit: 3000`.

**Под устойчивой нагрузкой (реальный ingestion ~55-60 запросов/мин) лимит
РЕАЛЬНО достигается** — во время live-прогонов этой сессии многократно
наблюдались `HTTP 429` и периодические `HTTP 5xx` (см.
`reports/phase5-live-summary.md`, раздел "Инциденты"). Это не гипотеза —
воспроизведено несколько раз, pipeline восстанавливался через retry/backoff
почти всегда, кроме одного класса сбоя (см. ниже).

## 3. `/explorer` — прямой SQL-доступ к БД OpenDota

`/explorer` действительно исполняет произвольный read-only SQL против
реплики Postgres OpenDota (не только API-обёртку) — подтверждено напрямую:
`SELECT count(*) FROM matches` вернул `251474` за один запрос, вместо тысяч
постраничных вызовов `/proMatches`. Использован для всех агрегатов ниже —
ни один из них не потребовал скачивания сырых данных.

Схема (via `information_schema.columns`) подтвердила поля, которые нужны
пайплайну: `matches.picks_bans` (JSON, поле `order`, не `ord` — `ord` это
только имя колонки в БД OpenDota, JSON API отдаёт `order`, что совпадает с
`RawPickBan.order` в нашем адаптере, см. раздел 6), `match_patch.patch`
(текстовая версия патча, отдельная таблица, НЕ то же самое, что наш
`patch_id`), `team_match`, `leagues.tier`.

## 5. Отсутствующие/недоступные поля (проверено, не предположено)

- `leagues.name` — OpenDota ЕГО ОТДАЁТ (`/matches/{id}.league.name`, например
  `"EPL Masters 2026"`), но наш собственный pipeline его НЕ сохраняет —
  `src/ingestion/opendota_pipeline.py` вызывает `repo.upsert_league(conn,
  nm.league_id, name=None, tier=nm.league_tier)`. Это разрыв в НАШЕМ коде,
  не ограничение источника — см. "Сравнение с Phase 1", это меняет прошлую
  оценку.
- `matches.patch` (целочисленный ID патча из самого OpenDota, например `60`)
  присутствует в ответе, но НЕ используется — мы вычисляем `patch_id`
  независимо через вендоренный `dotaconstants` (см. `docs/data-pipeline.md`).
  Оба метода дали согласованный результат на реальных данных (patch_id=60,
  версия "7.41", `released_at`=2026-03-24 в нашем справочнике vs
  2026-03-26 по live `match_patch` — расхождение 2 дня, незначимо).

## 6. Сравнение с исследованием Phase 1 (архитектурная переоценка не требуется)

| Предположение Phase 1 (из чтения исходников) | Живой факт | Расхождение | Влияние |
|---|---|---|---|
| Лимит 60/мин без ключа | Подтверждено (`x-rate-limit-remaining-minute` стартует с 59) | Нет | — |
| `/proMatches`, `ORDER BY match_id DESC`, до 100/страница | Подтверждено (постраничный live-прогон вернул ожидаемые объёмы) | Нет | — |
| `picks_bans[].order` (не `ord`) | Подтверждено прямым запросом `/matches/{id}` | Нет | — |
| `player_slot < 128` = radiant | Подтверждено (`player_slot: 0`, `account_id` не null) | Нет | — |
| `/leagues` отдаёт всю таблицу целиком | Подтверждено (используется `_league_tiers()`) | Нет | — |
| `/explorer` доступен для агрегатов | Подтверждено — реальный SQL, а не эмуляция | Нет | — |
| Историческая глубина не подтверждена, "REQUIRES LIVE VERIFICATION" | Подтверждено: 2012-05-28 — сегодня, 251 474 матчей | Первое реальное число | См. `docs/data-feasibility.md`, обновляется |
| `PRO_LEAGUE_TIERS = {premium, professional}` — дизайн-решение без данных | Подтверждено НЕОБХОДИМЫМ живыми данными: `excluded`-tier матчи реально засоряют `/proMatches` (до 85% в отдельных временных окнах, см. `reports/phase5-live-summary.md`) | Фильтр не просто разумен, а критичен | Дизайн не меняется, но обоснование теперь эмпирическое, не теоретическое |

**Вывод**: ни одно фактическое предположение Phase 1 не оказалось неверным
при живой проверке. Главное новое знание — фактические ЦИФРЫ (объём,
историческая глубина, доля excluded-tier по времени), которых не было и не
могло быть без сети.
