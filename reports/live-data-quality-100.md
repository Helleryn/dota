# LIVE DATA QUALITY — 100 РЕАЛЬНЫХ МАТЧЕЙ (и масштабирование до ~1265)

Все цифры в этом отчёте — из реального прогона
`python3 -m src.ingestion.run_opendota --source live ...` против
`api.opendota.com`, записанного в реальный локальный PostgreSQL этой сессии
(`docs/environment-constraints.md` больше не блокирует эту сессию — сеть
открыта, см. `reports/live-data-verification.md`).

## Как получены первые 100

`fetch_matches()` тянет ВЕСЬ диапазон `[since, until)` в память ДО
применения `--limit` (см. `src/ingestion/opendota_pipeline.py`, раздел
"Известные проблемы" ниже) — поэтому для первого прогона диапазон был
сужен вручную (`--since`/`--until` за 2 дня), чтобы не тянуть тысячи лишних
`/proMatches`-страниц ради 100 записей. Реальный темп pro-матчей в узком
окне оказался ниже ожидаемого (11 матчей за 2 дня) — окно расширено до 21
дня, что дало 254 матча, из которых оставлены 100 самых ранних
(детерминированно, `sorted(..., key=start_time)[:limit]`).

```
Матчей получено: 254
Матчей загружено: 100
Пропущено (блокирующие ошибки валидации): 0
Дублей match_id внутри батча: 0
```

## Ключевая находка: `excluded`-tier не распределён равномерно во времени

На выборке ~942 матчей (широкое окно, май-август 2026) tier-состав был
относительно сбалансирован (professional 360 / premium 147 / excluded 435).
На узком 17-дневном окне (6-23 мая 2026, после пересборки данных —
см. `reports/phase5-live-summary.md`, раздел "Инцидент с потерей данных")
`excluded` составил **85.6%** выборки (1083 из 1265) — весь этот избыток
происходит из ОДНОЙ лиги (`leagueid=18867`), которая генерирует десятки
одноразовых `team_id` с общими шаблонными именами ("Kiba Arms" — 5 разных
team_id, "Elite Eclipse" — 5, "Teiko" — 3, "Eye Gaming" — 4), каждый
сыграл 1-3 матча. Это похоже на автоматизированный открытый
квалификационный турнир, а не на профессиональную сцену.

**Вывод**: `PRO_LEAGUE_TIERS = {"premium", "professional"}` (уже
реализованный фильтр, `src/normalization/validate.py`) — не опциональная
оптимизация, а необходимое условие для датасета приемлемого качества.
Без него временные окна, пересекающиеся с такими турнирами, могут дать
>80% шумных строк. Наивный backfill по датам без учёта этого может
случайно затянуть период, доминируемый подобной лигой — стоит проверять
tier-состав окна ДО построения датасета, не только после.

## Известные проблемы (обнаружены живым прогоном, не гипотетические)

1. **`fetch_matches()` не ограничивает объём до применения `limit`.**
   Широкий `--since`/`--until` без явного сужения тянет ВСЕ матчи в
   диапазоне через `/proMatches` постранично, прежде чем оставить первые
   `limit`. На широком окне (по одному из прогонов) это дало
   `Матчей получено: 3103` при `--limit 400` — почти 8x лишней работы.
   Не исправлено в этой сессии (не блокирует, но стоит учесть в Phase 6+:
   либо останавливать пагинацию раньше при достижении limit, либо явно
   документировать необходимость сужать `--since`/`--until`).
2. **Транзиентные 429/5xx под нагрузкой — реальны, не гипотеза.**
   Наблюдались многократно при устойчивой нагрузке ~55-60 запросов/мин.
   Retry/backoff (`src/datasources/http_client.py`) в подавляющем
   большинстве случаев восстанавливал прогон; несколько раз это привело к
   `match_detail_unavailable` (best-effort деградация — ядро матча всё
   равно сохраняется, ожидаемое поведение по дизайну).
3. **Исчерпание retry на `/leagues` роняло весь CLI необработанным
   traceback** (не внутри per-match try/except, вызывается один раз в
   начале `fetch_matches`) — `ingestion_runs` оставался в статусе
   `running` навсегда, checkpoint не терялся (читается только из
   `succeeded`), но сбой не был виден без чтения логов. **Исправлено в
   этой сессии** — `run_ingestion` теперь оборачивает основную логику и
   пишет `status='failed'`, `error=str(e)` при любом необработанном
   исключении (`src/ingestion/opendota_pipeline.py`), проверено
   воспроизведением сбоя.
4. **`leagues.name` не заполняется** — подтверждено на реальных данных
   (все 18 строк в `leagues` имеют `name IS NULL`), хотя OpenDota реально
   отдаёт название лиги (`/matches/{id}.league.name`). Это разрыв в НАШЕМ
   коде (`opendota_pipeline.py` вызывает `upsert_league(..., name=None,
   ...)`), не ограничение источника — не исправлено в этой сессии
   (не блокирует Feature Set 0, влияет только на человекочитаемость).

## Идемпотентность на реальном API

Три последовательных запуска с идентичными `--since`/`--until`/`--limit`
(включая один прогон, где реально сработали 429 и 5xx retry) дали
идентичный набор из 100 загруженных матчей, **0 новых дублей**,
`raw_responses` полностью дедуплицирован по `content_hash` на повторных
прогонах (0 записано, 102 дедуплицировано на третьем прогоне). Устойчивость
подтверждена не на моках — на реальном нестабильном сетевом поведении.
