## 1. Проблема — и что аудит про неё показал

### 1.1 Масштаб раздробленности

| Метрика | Значение |
|---|---:|
| team_id всего | 7 933 |
| team_id, реально игравших pro/premium | 7 838 |
| Медиана матчей на team_id | **3** |
| team_id с 1-2 матчами | **3 576 (45.6%)** |
| Уникальных нормализованных имён | 6 440 |
| **Групп с одинаковым именем** | **686** |
| team_id в таких группах | 2 077 |
| Пар с одинаковым именем | 8 498 |

Экстремальные случаи: `eye gaming` — **52** разных team_id, `dominion` — 45,
`elite eclipse` — 44, `teiko` — 42.

### 1.2 Найденный дефект данных (исправлен в ходе аудита)

Аудит начался с того, что **только 93 из 7 933 team_id имели имя**.
Причина: bulk-backfill (`OpenDotaExplorerSource`, Phase 6-7) берёт имя из
`matches.radiant_team_name`/`dire_team_name`, а эти поля в БД OpenDota
**100% NULL** на всём диапазоне 2021-2026 (проверено прямым запросом).
Имена получили только команды из ingestion Phase 5 через `/proMatches`.

Исправлено `scripts/backfill_team_names.py` — имена загружены из отдельного
реестра `teams` OpenDota (22 397 записей, все с именем и тегом), покрытие
стало **7 933 / 7 933**.

### 1.3 КРИТИЧЕСКОЕ ограничение: point-in-time имён НЕ существует

Ни в нашей БД, ни у OpenDota:

* `matches.*_team_name` — 100% NULL (проверено);
* `teams.name` у нас — last-write-wins (`upsert_team` перезаписывает имя
  на каждом матче), то есть имя **на момент `last_seen_at`**;
* реестр `teams` OpenDota — снимок «на сегодня», без `valid_from` и без
  истории переименований.

**Следствие для всей фазы:** имя нельзя использовать как point-in-time
свидетельство. Оно годится лишь как слабое подтверждение поверх ростерных
доказательств — а те point-in-time по своей природе (`match_players`
привязаны к конкретному матчу с его timestamp).

## 2. Главное открытие аудита: параллельное существование опровергает merge

Кандидатов (пар team_id, деливших ≥3 игроков): **14 505**.

| Тип | Количество | Доля |
|---|---:|---:|
| **PARALLEL** — периоды жизни пересекаются | **8 112** | **55.9%** |
| SEQUENTIAL — один закончился, другой начался | 6 393 | 44.1% |

Две команды, игравшие **одновременно**, не могут быть одной сущностью —
сколько бы игроков они ни делили (это общие игроки/стеки, а не
преемственность). Это не эвристика, а логическое ограничение, проверяемое
по данным.

**Самое важное число фазы:** **461 пара имеет ОДИНАКОВОЕ имя, но играла
параллельно.** Слияние по имени было бы ошибочным во всех 461 случае.
Это эмпирическое доказательство правила «никогда не объединяй только по
названию» — на наших собственных данных, а не по общим соображениям.

Примеры: `Geek Fam` (4425527 и 8169775), `Execration` (7408845 и 8254145),
`Team Essence`, `Crocodile` — все играли в пересекающиеся периоды.

## 4. Ответ на ЧАСТЬ I: организация или состав?

Вопрос задания: «что именно мы хотим считать одной командой с точки зрения
предсказания матча?»

Аудит даёт эмпирический ответ. Наша задача — оценить **силу на момент
матча**. Phase 8/9 уже показали, что сила лучше всего описывается
**средним рейтингом текущих пяти игроков** (`elo_mean_diff`), а
`five_vs_team_elo_diff` — сильнейший одиночный признак. То есть носителем
силы фактически является **состав**, а не бренд.

Поэтому вводить полноценную двухуровневую модель
(`organization_id` + `competitive_team_id`) **нецелесообразно**: она решала
бы задачу «отследить бренд», которая нашей модели не нужна. Достаточно
одного уровня — `canonical_team_id`, склеивающего **преемственность
соревновательной сущности** (та же команда продолжила играть под новым
team_id). Это фиксируется как осознанное проектное решение, а не как
упрощение по недосмотру.

## 5. Стратегия: walk-forward identity (ответ на ЧАСТЬ P — leakage)

Задание отдельно требует разделить HISTORICAL IDENTITY KNOWLEDGE и
PREDICTION-TIME AVAILABLE IDENTITY. Разбор:

Наивный подход («построить mapping по всей истории и применить ко всем
матчам») использует будущее знание: в 2026 году мы знаем, что A и B — одна
сущность, и применяем это к матчу 2022 года.

**Решение — строить mapping walk-forward.** Связь A→B активируется ровно в
тот момент, когда доказательство становится наблюдаемым: когда B проводит
первый матч составом, сильно пересекающимся с последним составом A.
Формально:

```
valid_from(link A→B) = start_time первого матча B, на котором
                       выполнено условие overlap(roster_B, last_roster_A) >= порог
```

Свойства такой конструкции:

1. При прогнозе матча в момент `t` используются только связи с
   `valid_from <= t` — будущие ребрендинги невидимы.
2. Ретроспективно рейтинг **не переписывается**: A накапливает историю до
   `t`, B наследует её начиная с `t`.
3. Доказательство (совпадение состава) действительно доступно к моменту
   `t` — состав объявляется до матча, то же соглашение, что в Phase 7/8/9.

Это делает identity-слой leakage-safe **по построению**, а не по проверке
постфактум. Adversarial-тесты обязаны это подтвердить.

## 6. Правила слияния (консервативные, ЧАСТЬ R)

False merge опаснее false split, поэтому:

| Условие | Действие |
|---|---|
| Периоды пересекаются (parallel) | **НИКОГДА не сливать** — независимо от имени и overlap |
| overlap ≥ 0.6 И разрыв ≤ 90 дней И имя совпало | HIGH → сливать |
| overlap ≥ 0.6 И разрыв ≤ 90 дней | MEDIUM → сливать |
| Совпало только имя | LOW → **НЕ сливать** |
| Прочее | UNRESOLVED → не сливать |

Предварительное распределение (до применения walk-forward-ограничения):
HIGH 166, MEDIUM 877, LOW 1 708, UNRESOLVED 3 642, REJECTED_PARALLEL 8 112.

Практический масштаб: team_id из HIGH/MEDIUM пар участвуют в **66 444 из
234 742 team-matches (28.3%)** — достаточно, чтобы эффект был измерим.

## 7. План экспериментов

Frozen baseline (Elo + Form3) не меняется. Набор Phase 9
(`elo_mean_diff`, `five_vs_team_elo_diff`, `hero_exp_decay_diff`) не
меняется до отдельного эксперимента. Все варианты — на одном evaluation set.

| Вариант | Состав |
|---|---|
| A | Phase 9 feature set (как есть) |
| B | Phase 9 + Team Elo на **canonical** id вместо source id |
| C | Phase 9 + `five_vs_team_elo` пересчитанный на canonical id |
| D | Phase 9 + Team×Hero (residual, со shrinkage и затуханием) |
| E | Phase 9 + canonical identity + Team×Hero |

Протокол — как в Phase 9 (исправленный): **отбор только по VALIDATION,
TEST один раз в конце**, block bootstrap, McNemar, walk-forward по годам.

## 8. Риски

1. **False merge** портит историю обеих команд необратимо и незаметно —
   защита: запрет parallel + высокий порог overlap + консервативные уровни.
2. **Эффект может оказаться нулевым**: Phase 9 показала, что ≈1.05 pp из
   +2.13 pp roster-эффекта не объясняются проблемой идентичности — то есть
   потолок улучшения от identity ограничен.
3. **Team×Hero может не дать сигнала** даже после resolution (медиана 3
   матча на team_id означает, что даже после слияния выборки малы) —
   в этом случае честно фиксируется REMOVE/RESEARCH FURTHER.
4. **Recall слияний неизмерим** без внешней истины — оценивать будем
   precision на ручном gold set, recall честно пометим как неоценимый.
