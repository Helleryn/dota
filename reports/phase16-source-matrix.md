## 3. Надёжность и политика обращения (PART S)

| Источник | Наблюдаемое поведение | Политика в коде |
|---|---|---|
| Valve DPC | 200 стабильно, ответ 1–4 с, 160 КБ | интервал 0.5 с, таймаут 60 с |
| bo3.gg | 200 стабильно, быстрый | интервал 0.3 с, таймаут 40 с |
| **Liquipedia** | **429 на 2 из 3 запросов при 3 с** | **интервал 30 с**, обязательный кэш |
| OpenDota | стабильно, изредка таймаут | интервал 1.1 с, таймаут 60 с |

Реализованные механизмы:

| Механизм | Как сделано |
|---|---|
| **backoff** | при 429 интервал хоста **увеличивается**, читается `Retry-After` |
| **никакого обхода** | интервал только растёт; тест `test_rate_limit_increases_interval_never_decreases_it` |
| **cache** | Liquipedia кэширует wikitext; тест на отсутствие повторного запроса |
| **fallback** | статусы `UNAVAILABLE` / `RATE_LIMITED` / `EMPTY` различимы вызывающим |
| **circuit breaker** | не реализован — отмечено как незакрытое |
| **schema stability** | не отслеживается автоматически; статус `SCHEMA_CHANGED` объявлен, но не используется |

Отдельно: **429 — это результат, а не препятствие.** Он возвращается
вызывающему статусом, а не превращается в исключение и не обходится.

## 4. Ключевое ограничение матрицы

Ни один источник не покрывает всё:

```
расписание  -> bo3.gg (много) + Valve (точно, редко)
ростер      -> bo3.gg (10% полных)
интервалы   -> Liquipedia (медленно)
роли        -> Liquipedia, но только PREDICTED
патч        -> OpenDota
результаты  -> OpenDota
```

Отсюда мультиисточниковая архитектура — не архитектурное предпочтение,
а прямое следствие замеров. Гипотеза **S6 подтверждена**.
