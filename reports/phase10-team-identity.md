## 1. Executive summary

Построен leakage-safe walk-forward слой `source_team_id → canonical_team_id`.
Он **работает как задумано** и **измеримо улучшает Team Elo**, но
**не улучшает итоговый прогноз**, потому что его вклад полностью поглощён
player-Elo из Phase 8.

| Вопрос фазы | Ответ |
|---|---|
| Позволяет ли корректная идентичность точнее оценивать силу команды? | **Да.** Без player-Elo: Δlog loss = −0.0038, 95% CI **[−0.0051, −0.0026]** (полностью отрицателен), AUC +0.0102 на затронутых матчах |
| Добавляет ли это реальный out-of-sample сигнал к прогнозу? | **Нет.** В присутствии player-Elo: Δacc = −0.0002, CI [−0.0015, +0.0010], McNemar p=0.77 |
| Даёт ли canonical identity надёжный Team×Hero сигнал? | **Нет.** Team×Hero статистически **ухудшает** accuracy (Δacc = −0.0020, CI [−0.0036, −0.0004], p=0.016) |

**Главный вывод:** Phase 8 уже решила проблему идентичности команд для целей
прогноза — не через исправление `team_id`, а обойдя его. Player-Elo
отслеживает **людей, а не регистрации**, и потому иммунен к раздробленности
`team_id` по построению. Canonical identity решает ту же проблему прямо, но
приходит вторым и оказывается избыточной.

### 2.1 Найденный и исправленный дефект данных

Аудит начался с того, что **только 93 из 7 933 team_id имели имя**.
Причина: bulk-backfill (`OpenDotaExplorerSource`, Phase 6-7) читает имя из
`matches.radiant_team_name`/`dire_team_name`, а эти поля в БД OpenDota
**100% NULL** на всём 2021-2026 (проверено прямым запросом по каждому году).

Исправлено `scripts/backfill_team_names.py`: имена загружены из отдельного
реестра `teams` OpenDota (22 397 записей, все с name и tag). Покрытие стало
**7 933 / 7 933**. Дефект не влиял на прошлые фазы (имя не входило ни в один
признак), но делал невозможным сам аудит идентичности.

### 2.2 Point-in-time имён не существует — ни у нас, ни у OpenDota

* `matches.*_team_name` — 100% NULL;
* наш `teams.name` — last-write-wins (`upsert_team` перезаписывает на каждом
  матче), то есть имя на момент `last_seen_at`;
* реестр `teams` OpenDota — снимок «на сегодня», без истории переименований.

**Следствие:** имя принципиально не может быть point-in-time доказательством.
Оно используется только для повышения уверенности HIGH vs MEDIUM, но никогда
как самостоятельное основание слияния. Ростер, напротив, point-in-time по
природе — `match_players` привязаны к конкретному матчу.

## 5-7. Alias / roster / temporal continuity

Использованы три сигнала, в порядке доказательной силы:

1. **Roster overlap** (Jaccard последнего состава A и состава B) — основной,
   point-in-time.
2. **Временная связь** — разрыв ≤ 90 дней И отсутствие пересечения периодов.
3. **Совпадение имени** — только повышает HIGH vs MEDIUM.

Нормализация имён консервативна: регистр, unicode NFKC, пробелы,
разделители. **Не удаляем** «Team»/«Academy» — `Entity` и `Entity Academy`
могут быть разными сущностями. Audit log нормализации: 7 030 записей.

## 8. Identity scoring methodology

```
ЕСЛИ периоды пересекаются            -> REJECTED_PARALLEL (никогда не сливать)
ЕСЛИ overlap>=0.6 И gap<=90д И имя   -> HIGH    (сливать)
ЕСЛИ overlap>=0.6 И gap<=90д         -> MEDIUM  (сливать)
ЕСЛИ только имя                       -> LOW     (НЕ сливать)
ИНАЧЕ                                 -> UNRESOLVED (НЕ сливать)
```

Пороги (0.6 / 90 дней) заданы **априорно** из соображений предметной области
и **не подбирались по TEST** — прямое требование задания.

## 10. Precision / recall

Применено к реальным данным: **893 связи** (HIGH 266, MEDIUM 627),
7 793 source id → **6 900 canonical** (сокращение 11.5%).

**Precision (ручная проверка выборки):**

* **HIGH — ошибок не найдено.** Все проверенные — очевидные повторные
  регистрации с вариациями написания: `P1 Gaming`→`P1 GAMING`,
  `Starx`→`StarX`, `GOJO`→`GoJo`, `Your soul is mine`→`Your Soul Is Mine`,
  `Execration`→`Execration`.
* **MEDIUM — качество смешанное.** Есть безусловно верные:
  **`mudgolems` → `Tundra Esports`** — реальный, широко известный ребрендинг,
  корректно найденный только по ростеру и времени, без подсказки имени.
  Но обнаружен и **режим ложного слияния**: `Gambit Esports` → `Gambit-2` и
  `Ensis` → `Ensis Academy` — это, вероятно, основной состав против
  второго/академического, а не преемственность. Тот же состав временно
  выступает под двумя тегами.

**Recall — не оценивается.** Без внешней истины (Liquipedia недоступна:
HTTP 429; STRATZ: HTTP 403) невозможно узнать, сколько реальных
переименований мы пропустили. Придумывать оценку не буду — это прямое
требование задания. Известно лишь, что резолвер **сознательно
консервативен**: из 6 393 последовательных кандидатов слито 893 (14%).

**False merge rate:** не поддаётся точному измерению по той же причине;
качественно — близок к нулю для HIGH, ненулевой для MEDIUM
(идентифицирован режим «основной состав vs второй состав»).

## 12-13. Canonical entity design и temporal validity

**Решение: один уровень `canonical_team_id`, без разделения на
`organization_id` / `competitive_team_id`.**

Обоснование (ЧАСТЬ I задания — «что мы хотим считать одной командой»):
Phase 8/9 показали, что носителем предсказательной силы является **состав**
(`elo_mean_diff` — крупнейший коэффициент модели), а не бренд.
Двухуровневая модель решала бы задачу «отследить бренд», которая нашей
модели не нужна. Это осознанное проектное решение, а не упрощение.

Структура связи (`IdentityLink`): `source_team_id`, `canonical_team_id`,
`predecessor_team_id`, **`valid_from`**, `confidence`, `roster_overlap`,
`gap_days`, `name_matched`, `resolution_method`.

**Исходный `team_id` никогда не теряется:** `canonical(id)` для несвязанного
или неизвестного id возвращает сам id (проверено тестом
`test_source_id_never_lost`).

### Объяснение (проверено, не постулировано)

Сравнение двух экспериментов даёт прямой ответ:

| Контекст | Помогает ли canonical identity? |
|---|---|
| **Без** player-Elo (только Elo + Form3) | **Да**: Δlog loss CI = [−0.0051, −0.0026], AUC +0.0102 на затронутых |
| **С** player-Elo (набор Phase 9) | **Нет**: Δacc CI = [−0.0015, +0.0010], p=0.77 |

Player-Elo (Phase 8) агрегирует рейтинги **людей**, а не регистраций.
Когда организация перерегистрируется под новым `team_id`, team-Elo обнуляется,
а player-Elo — нет: рейтинги едут за игроками. То есть Phase 8 решила ту же
проблему **обходом**, и решила её раньше. Canonical identity исправляет
`team_id` напрямую, но информация уже присутствует в модели.

Коэффициенты варианта E подтверждают: `elo_mean_diff` +0.259 (крупнейший),
`elo_difference_canon` +0.210, `five_vs_team_elo_diff_canon` +0.104.

## 16. Team×Hero experiment

Построен **residual**, а не raw winrate (ЧАСТЬ M):

```
residual = shrunk_winrate(team, hero) − strength(hero)
```

затухание 180 дней, shrinkage prior = 20 игр.

Результат: коэффициент +0.035, но **статистически значимо ухудшает
accuracy** (D: Δacc = −0.0020, CI [−0.0036, −0.0004], p=0.016).

Причина правдоподобна и согласуется с аудитом: медиана **3 матча на
team_id**, и даже после слияния (сокращение лишь на 11.5%) выборок
team×hero недостаточно. Shrinkage защищает от абсурдных значений, но там,
где данных почти нет, признак вносит шум, а не сигнал.

**Team×Hero → REMOVE.** Гипотеза «canonical identity разблокирует Team×Hero»
проверена и **не подтвердилась**.

## 17. Leakage audit

Идентичность строится **walk-forward**: связь A→B активируется в момент
первого матча B с пересекающимся составом:

```
valid_from(A→B) = start_time первого матча B, где overlap(roster_B, last_roster_A) >= 0.6
```

`tests/leakage/test_phase10_identity.py` — **15/15 PASS**, ключевые:

| Тест | Что доказывает |
|---|---|
| **`test_identity_is_prefix_stable`** | Идентичность на префиксе истории **тождественна** соответствующей части идентичности на полной истории — формальное определение отсутствия утечки |
| `test_future_matches_do_not_change_past_identity` | Будущие матчи не меняют установленные связи |
| `test_future_rebrand_does_not_retroactively_merge` | `valid_from` совпадает с моментом появления доказательства; прошлое не переписывается |
| `test_future_name_change_cannot_create_past_link` | Имя (снимок «сегодня») не может создать связь без ростерных доказательств |

Разделение, которого требует ЧАСТЬ P:

* **HISTORICAL IDENTITY KNOWLEDGE** — «в 2026 известно, что A и B одна
  организация». Не используется.
* **PREDICTION-TIME AVAILABLE IDENTITY** — «в момент t состав B совпадает с
  последним составом A». Используется только это.

Применение итогового словаря `canonical()` как статического отображения
корректно, потому что каждому `team_id` canonical назначается в момент
**его первого матча** и далее не меняется — то есть словарь и есть результат
walk-forward построения (подтверждено prefix-stability тестом).

Полный прогон проекта: **95/95 тестов PASS**.

## 19. Coverage limitations

| Ограничение | Статус |
|---|---|
| Point-in-time имена команд | **Не существуют** ни у нас, ни у OpenDota |
| История переименований | Отсутствует |
| Liquipedia | HTTP 429 на первом запросе (жёсткие лимиты + ToS) |
| STRATZ | HTTP 403 (нужен ключ) |
| Регион команды | Отсутствует в схеме |
| Recall слияний | **Неизмерим** без внешней истины |
| Основной/академический состав | Идентифицированный режим ложного слияния MEDIUM |

## 20. Recommended production strategy

1. **Оставить `canonical_team_id` в pipeline, но не в feature set.**
   Слой полезен сам по себе (улучшает Team Elo, CI по log loss отрицателен) и
   пригодится, если player-Elo когда-либо будет недоступен — например, при
   прогнозе матча без анонса лайнапа, где roster-признаки неприменимы.
2. **Feature set не менять.** Рекомендованный набор Phase 9 остаётся:
   `elo_mean_diff`, `five_vs_team_elo_diff`, `hero_exp_decay_diff` поверх
   frozen baseline.
3. **Ограничить слияния уровнем HIGH** в проде, если слой будет
   использоваться: precision у HIGH не имеет найденных ошибок, у MEDIUM —
   есть режим «основной vs второй состав».
4. **Не инвестировать в Team×Hero** до кратного роста выборки на команду.
