# Team Identity Issues — Phase 5

Per `docs/team-identity.md` (Phase 4): не пытаемся агрессивно решить
identity resolution в Phase 5 — загружаем доступные team/player связи,
сохраняем raw-информацию, фиксируем ограничения.

## Что реально загружено в Phase 5

- `teams`: 4 записи (`team_id`, `name`, `tag`) — 1:1 с `team_id` источника,
  как и решено в `docs/team-identity.md` ("один `team_id` = одна
  `organization_id` по умолчанию"). Таблица `organizations` из схемы Phase 4
  **не заполняется в Phase 5** — намеренно, resolution-слой не строится,
  пока нет реальных случаев переименования/merger для проверки логики на них.
- `players`: 79 уникальных `account_id`, имена везде `NULL` (fixture не
  содержит `notable_players`-подобных данных с именами — в реальном OpenDota
  часть игроков, отмеченных как "заметные", имеет имя, большинство — нет).
- `team_roster_periods`: **не заполняется в Phase 5.** Реконструкция ростера
  из истории матчей (`docs/team-identity.md`, источник
  `reconstructed_from_matches`) требует более длинной истории матчей на
  команду, чем 3-4 матча в текущем fixture-наборе, чтобы результат
  реконструкции был содержательным — реализация отложена до Phase 6+,
  когда будет реальный больший датасет.

## Обнаруженные проблемы (реальные, из прогона)

1. **Нет данных о переименовании/merger** — в fixture-наборе все 4 команды
   стабильны на всём периоде (2024-01-01 — 2024-02-09), поэтому основной
   риск-сценарий из `docs/team-identity.md` (п.1-3: rename/новая
   регистрация/merger) **не был и не мог быть проверен на реальных данных**
   в этой фазе. Это прямое следствие короткого fixture-периода, не
   доказательство, что логика работает на реальных многолетних данных —
   требует отдельной проверки на живом датасете (Phase 6+).
2. **1 анонимный игрок** (`account_id IS NULL`) в 80 player-match записях
   (match 7001, слот 4) — валидный случай (приватность Steam), но означает,
   что реконструкция ростера для этой команды в этом матче будет неполной
   (4 из 5 игроков), если использовать этот матч как якорь состава.
3. **`teams.organization_id` везде `NULL`** — таблица `organizations`
   спроектирована (Phase 4), но фаза заполнения (Phase 5) её сознательно не
   трогает. Downstream-код (Feature Set 0/1) не использует
   `organization_id` — риска для текущего MVP нет, это будущая зависимость
   Feature Set 2 (roster-признаки).

## PHASE 5 LIVE (2026-08-24) — обновление на реальных данных

Реальный прогон против `api.opendota.com` (~1265 матчей, май-август 2026,
`reports/live-data-quality-100.md`) впервые дал материал для проверки п.1
выше — вот что нашлось.

### Реальные случаи повторяющегося имени под разными team_id

Прямой SQL по накопленной выборке (`SELECT name, count(DISTINCT team_id)
FROM teams GROUP BY name HAVING count(DISTINCT team_id) > 1`) нашёл **18
таких имён**. Разобраны детально три показательных случая:

1. **"Rune Eaters"** — `team_id` 9895247 и 10207961, разные лиги (19944 и
   19917), пересекающиеся по времени матчи. Похоже на СЛУЧАЙНОЕ совпадение
   имени двух разных, никак не связанных организаций — не переименование
   одной команды. Консервативная стратегия (1:1 `team_id` = `organization_id`,
   без авто-merge) — правильное поведение здесь: слияние по имени дало бы
   ЛОЖНОЕ объединение двух разных команд.
2. **"Xtreme Gaming"** — `team_id` 8261500 (известная топ-организация,
   стабильно играет в лигах 19785→19719 professional/premium на всём
   периоде) плюс ОТДЕЛЬНЫЙ `team_id` 10208071 с тем же именем, 1 матч, лига
   19917 (professional). Это САМЫЙ рискованный найденный случай: реальная
   узнаваемая команда имеет "тёзку" даже в pro-tier лиге, не только в
   мусорных excluded-турнирах. Наивный merge-по-имени здесь мог бы
   ошибочно приписать чужой матч истории/рейтингу известной команды.
3. **Кластер имён из лиги `leagueid=18867` (`tier=excluded`)**: "Kiba Arms"
   (5 team_id), "Elite Eclipse" (5), "Teiko" (3), "Eye Gaming" (4), "Ghost
   Sheep", "Air Defence", "Dominion", "Satan666", "Nethercore",
   "Shinigami Gaming", "PlayTime", "BloodyRose", "Nigma Galaxy" — каждый
   `team_id` сыграл 1-3 матча. Похоже на автоматизированный открытый
   турнир с шаблонными/generic именами команд, не на реальные организации
   с историей. Все эти случаи — в `tier='excluded'`, т.е. УЖЕ отфильтрованы
   из pro-датасета `PRO_LEAGUE_TIERS`-фильтром — этот шум не попадает в
   Feature Set 0.

### Вывод (обновляет п.1 выше)

Гипотеза "не было случая для проверки логики" **больше не верна** — случаи
есть, и они подтверждают, что консервативная стратегия
(`docs/team-identity.md`: 1:1 `team_id`↔`organization_id` по умолчанию, без
агрессивного авто-merge) была ПРАВИЛЬНЫМ решением: почти все совпадения
имён на реальных данных — это РАЗНЫЕ команды, не переименования одной. Один
случай ("Xtreme Gaming") зафиксирован как известный риск для будущей
identity-resolution логики (Phase 6+, если строится по имени, а не только
по `team_id`) — НЕ исправлено автоматическим слиянием в этой сессии, как и
требует задание (раздел 13: "не делай агрессивный автоматический merge").

`team_roster_periods` по-прежнему не заполняется — не изменилось в этой
сессии (вне текущего scope, roster reconstruction рассмотрен отдельно, см.
`reports/phase5-live-summary.md`, раздел "Roster reconstruction").
