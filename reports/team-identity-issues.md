# Team Identity Issues — Phase 5

Per `docs/team-identity.md` (Phase 4): не пытаемся агрессивно решить
identity resolution в Phase 5 — загружаем доступные team/player связи,
сохраняем raw-информацию, фиксируем ограничения.

## Что реально загружено в Phase 5

- `teams`: 4 записи (`team_id`, `name`, `tag`) — 1:1 с `team_id` источника,
  как и решено в `docs/team-identity.md` ("один `team_id` = одна
  `organization_id` по умолчанию"). Таблица `organizations` из схемы Phase 4
  **не заполняется в Phase 5** — намеренно, resolution-слой не строится,
  пока нет реальных случаев переименования/merger для проверки логики на них.
- `players`: 79 уникальных `account_id`, имена везде `NULL` (fixture не
  содержит `notable_players`-подобных данных с именами — в реальном OpenDota
  часть игроков, отмеченных как "заметные", имеет имя, большинство — нет).
- `team_roster_periods`: **не заполняется в Phase 5.** Реконструкция ростера
  из истории матчей (`docs/team-identity.md`, источник
  `reconstructed_from_matches`) требует более длинной истории матчей на
  команду, чем 3-4 матча в текущем fixture-наборе, чтобы результат
  реконструкции был содержательным — реализация отложена до Phase 6+,
  когда будет реальный больший датасет.

## Обнаруженные проблемы (реальные, из прогона)

1. **Нет данных о переименовании/merger** — в fixture-наборе все 4 команды
   стабильны на всём периоде (2024-01-01 — 2024-02-09), поэтому основной
   риск-сценарий из `docs/team-identity.md` (п.1-3: rename/новая
   регистрация/merger) **не был и не мог быть проверен на реальных данных**
   в этой фазе. Это прямое следствие короткого fixture-периода, не
   доказательство, что логика работает на реальных многолетних данных —
   требует отдельной проверки на живом датасете (Phase 6+).
2. **1 анонимный игрок** (`account_id IS NULL`) в 80 player-match записях
   (match 7001, слот 4) — валидный случай (приватность Steam), но означает,
   что реконструкция ростера для этой команды в этом матче будет неполной
   (4 из 5 игроков), если использовать этот матч как якорь состава.
3. **`teams.organization_id` везде `NULL`** — таблица `organizations`
   спроектирована (Phase 4), но фаза заполнения (Phase 5) её сознательно не
   трогает. Downstream-код (Feature Set 0/1) не использует
   `organization_id` — риска для текущего MVP нет, это будущая зависимость
   Feature Set 2 (roster-признаки).

## Следующий шаг для team identity

Не в Phase 5 — при первом реальном (не fixture) прогоне на данных из
`api.opendota.com` за период от нескольких месяцев: (а) проверить, есть ли
среди реальных команд повторяющиеся имена под разными `team_id` (кандидаты
на merger/re-registration, `docs/team-identity.md` п.2), (б) начать
реконструкцию `team_roster_periods` из фактических составов матчей.
