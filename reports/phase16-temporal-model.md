# PHASE 16 — временная модель и разрешение противоречий

---

## 1. Три метки времени (PART I)

У каждого внешнего факта их ровно три, и смешивать их нельзя:

| Метка | Смысл | Чем НЕ является |
|---|---|---|
| `observed_at` | когда **наша система** увидела факт | не когда факт возник |
| `effective_at` | с какого момента факт **действует** | не когда мы узнали |
| `event_at` | когда происходит **само событие** | не когда объявили |

Канонический пример из задания:

```
замена объявлена  14:00   -> observed_at
действует с матча 18:00   -> effective_at
матч              18:00   -> event_at

прогноз 13:00 -> замену знать НЕ МОЖЕТ
прогноз 15:00 -> замену знать ОБЯЗАН
```

Без разделения `observed_at` и `effective_at` это не выражается вовсе.

## 2. Запрос «на момент T» требует двух условий

```python
def roster_as_of(self, ref, t, require_known=True):
    for m in self._by_team[key(ref)]:
        if not m.active_at(t):        # факт ДЕЙСТВОВАЛ
            continue
        if require_known and not m.known_at(t):   # факт был ИЗВЕСТЕН
            continue
        yield m
```

`require_known=True` по умолчанию. Отключение допустимо только для
исторического анализа, где вопрос другой — «кто фактически числился», —
и должно быть **явным**. Тест
`test_historical_query_can_opt_out_of_known_at` фиксирует, что это не
поведение по умолчанию.

### Проверка на живых данных

Ростер, загруженный с bo3.gg сейчас:

```
состав на СЕЙЧАС:                        5 игроков
на вчера (факт ещё не наблюдался):       0 игроков
```

Ровно требуемое поведение: вчерашний прогноз не мог знать того, что мы
прочитали сегодня.

## 3. Одно осознанное допущение

`valid_from is None` трактуется как «неизвестно, когда пришёл» и
считается активным до `valid_to`. Иначе игрок с неизвестной датой
прихода выпадал бы из всех запросов.

Допущение названо в коде и **понижает доверие**: факт с неизвестной
датой не может иметь `HIGH`.

## 4. Доверие к источнику ≠ уверенность модели (PART M)

| Понятие | Что измеряет | Диапазон |
|---|---|---|
| `SourceConfidence` | надёжность **факта** | HIGH / MEDIUM / LOW / UNKNOWN |
| `confidence` прогноза | уверенность **модели** | `\|p − 0.5\|` |

Смешивать нельзя: модель может быть очень уверена в матче, о составе
которого мы почти ничего не знаем. Это два независимых основания для
отказа от прогноза.

Присвоенные уровни:

| Источник | Уровень | Почему |
|---|---|---|
| Valve DPC | **HIGH** | официальный источник Valve |
| bo3.gg | MEDIUM | структурированное API сообщества |
| Liquipedia | MEDIUM | структурно, но редактируется сообществом |
| вывод по косвенным данным | LOW | — |
| происхождение неизвестно | UNKNOWN | **в признаки не идёт** |

Доверие к составу целиком = **минимум** по игрокам, а не среднее.

## 5. Разрешение противоречий (PART N)

Правило фазы: **не выбирать молча.** Порядок правил:

| # | Правило | Пример |
|---|---|---|
| 1 | официальный источник побеждает | Valve (HIGH) > bo3.gg (MEDIUM) |
| 2 | подтверждение несколькими источниками | два источника против одного |
| 3 | свежесть наблюдения | более позднее `observed_at` |
| 4 | **явный отказ** | `UNKNOWN` + описание конфликта |

Четвёртый пункт важнее первых трёх: он превращает «система молча выбрала
одно из двух» в «система знает, что не знает». Неразрешённый конфликт
попадает в `unresolved_conflicts` снимка и является основанием понизить
доверие к данным вплоть до `ABSTAIN`.

Проверено тестами:

| Сценарий | Тест |
|---|---|
| два равных источника расходятся → UNKNOWN | `test_source_disagreement_is_not_resolved_silently` |
| официальный побеждает сообщество | `test_official_source_wins_over_community` |
| двое против одного | `test_corroboration_beats_a_single_dissenter` |
| согласие не требует правила | `test_agreement_needs_no_rule` |
| нет данных ни у кого → UNKNOWN | `test_missing_roster_is_unknown_not_empty_success` |

## 6. Патч (PART G)

`patch_as_of(patches, t)` берёт последний релиз **не позже t** и требует,
чтобы запись была наблюдена к моменту t.

Два отдельных вида утечки, оба закрыты тестами:

| Утечка | Тест |
|---|---|
| будущий патч попал в прогноз | `test_future_patch_cannot_enter_prediction` |
| патч вышел до T, но данные о нём получены позже | `test_patch_known_only_later_is_not_used` |

Источник: OpenDota `/constants/patch` — 61 патч с датами, подтверждено
живым запросом. Даты релизов — исторические факты, поэтому источник
пригоден для запросов «на момент T».

## 7. Hero meta «на момент T» (PART H)

`hero_exp_decay_diff` **не меняется** — это замороженный признак.

Вопрос фазы был иным: откуда production берёт историю силы героев.
Ответ: **из собственной базы проекта**, а не из внешнего «винрейта
сегодня». Признак считается walk-forward проходом по матчам строго
раньше t (модуль `hero_strength_schemes`, Phase 9), и его корректность
уже доказана тестами утечки тех фаз.

Внешний источник здесь не нужен и был бы вреден: любой «текущий винрейт
героя» — это агрегат по неизвестному окну, непригодный для as-of-T.

Мониторинг Phase 15 показал, что сигнал устойчив: корреляция с исходом
держится около +0.10 по шести периодам и не падает после патча.
