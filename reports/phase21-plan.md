## 1. STEP 1 — аудит фактического baseline

### 1.1 Расхождение задания и кода — зафиксировано, не переписано

Задание (§2) описывает baseline как «team Elo + recent form + player Elo
+ **player uncertainty / H1** + остальные подтверждённые pre-match
признаки».

**В коде это не так.** Проверено по `src/shadow/versions.py` и
`scripts/phase20_pipeline.py`:

```python
FROZEN_FEATURES = [elo_difference, form_3_difference, elo_mean_diff,
                   five_vs_team_elo_diff, hero_exp_decay_diff]   # 5, POST-DRAFT
```

`hero_exp_decay_diff` требует драфта, поэтому **pre-match frozen** — это
четвёрка Phase 17/18/20:

```python
M0 = [elo_difference, form_3_difference, elo_mean_diff, five_vs_team_elo_diff]
```

**H1 в frozen НЕ входит.** Phase 20 подтвердила её на TEST
(Δlog loss −0.00420, CI [−0.00586, −0.00261]) и явным правилом PART N
запретила менять frozen до отдельного аудита. Она остаётся
**кандидатом**, а не частью baseline. Phase 21 это положение не меняет.

### 1.2 Три уровня сравнения

| Обозначение | Состав | Что это |
|---|---|---|
| **B0** | M0 — 4 признака | **фактический** pre-match frozen в коде |
| **B1** | M0 + H1 (3 признака неопределённости) | кандидат Phase 20; ровно то, что §20/§32 называют baseline |
| **B2** | M0 + H1 + H3 (10 признаков) | конфигурация, **подтверждённая на TEST** в Phase 20 |

**Основная база для incremental value — B2.** Причина: H3 (временная
актуальность) входила в подтверждённый набор, и исключить её из базы
означало бы дать новым признакам поглотить сигнал давности и выглядеть
сильнее, чем они есть. B1 приводится дополнительно, потому что именно
его называет §20.

Признак, который бьёт B1, но не бьёт B2, — избыточен с давностью, и это
будет сказано прямо.

Что именно входит в H1 и H3 (Phase 20, не переопределяется):

```
H1 = rd_mean_diff, rd_max_diff, elo_mean_diff_attenuated
H3 = elo_mean_decayed_diff, recency_gap, days_since_last_max_diff
```

Формулы H1 **не трогаются** (§3): ни полураспад 90 дней, ни κ=10 не
переоптимизируются.

## 3. STEP 2 — матрица гипотез

Окна объявлены заранее и не расширяются: **7 / 14 / 30 дней**.
Полураспад затухания — **90 дней**, взят из Phase 9/20 и **не
подбирается**: подбор был бы скрытым экспериментом сверх объявленных.

| # | Гипотеза | Механизм | Статус |
|---|---|---|---|
| **H1** | неопределённость игрока | Phase 20, KEEP-кандидат | контроль, не переоптимизируется |
| **H2** | recent opponent-adjusted strength | `Σ w·(actual − expected)/Σ w`, expected по **исторической** силе соперника | **проверяется** |
| **H3** | common opponent signal | сравнение перформанса R и D против **общих** соперников | **проверяется** |
| **H4** | H2H residual | фактический результат встреч минус ожидание по Elo | **проверяется** |
| **H5** | time-decayed H2H | winrate встреч с затуханием | **проверяется** |
| **H6** | roster-aware H2H | H2H, взвешенный пересечением текущего состава с составом той встречи | **проверяется** |
| **H7** | простой recent winrate | **негативный контроль**, превосходства не ожидается | проверяется как контроль |
| **H8** | patch-aware recent performance | только **если** H2 или H3 дали сигнал | условная |

### 3.1 H2 — формализация

Для команды X в момент T и окна W:

```
oas(X,T,W) = Σ_m w(m)·(actual(m) − expected(m)) / Σ_m w(m)

expected(m) = 1 / (1 + 10^((elo_opp(t_m) − elo_X(t_m)) / 400))
w(m)        = 0.5^((T − t_m)/90д)
```

Критично: `elo_opp(t_m)` — сила соперника **на момент того матча**, из
walk-forward снимка, а не сегодняшняя. Это то, что §16 называет
обязательным и что проверяется тестом 4.

Признаки: `oas_diff_7`, `oas_diff_14`, `oas_diff_30`.

### 3.2 H3 — формализация

Пусть `S_R` — соперники R за 30 дней до T, `S_D` — соперники D.
Общие: `C = S_R ∩ S_D`.

```
common_opponent_delta = mean_{B∈C} [ perf_R(B) − perf_D(B) ]
common_opponent_count = |C|
```

`perf_X(B)` — тот же residual `actual − expected`, усреднённый по всем
встречам X с B в окне, с тем же затуханием.

`count` — **канал надёжности, а не признак сам по себе** (§7). Его
полезность проверяется отдельно, а не постулируется.

### 3.3 H4–H6 — формализация

```
h2h_residual_decayed   Σ w·(actual − expected) / Σ w  по прошлым встречам пары
h2h_winrate_decayed    Σ w·actual / Σ w                  (H5)
h2h_matches_decayed    Σ w                                (надёжность)
h2h_days_since_last    давность последней встречи
h2h_roster_overlap     доля игроков текущей пятёрки, игравших ту встречу
h2h_residual_roster    residual, взвешенный ещё и на overlap        (H6)
```

`h2h_roster_overlap` строится **только** из составов прошлых матчей и
текущего заявленного состава на момент T. Сегодняшний состав к старым
встречам ретроактивно не применяется (тест 14).

## 4. Политика пропусков (§14, §15)

Три состояния различаются явно и **не** сливаются:

| Состояние | Как выражено |
|---|---|
| **missing** — команда не сыграла ни одного матча в окне | признак = `NaN` |
| **zero** — сыграла, и residual вышел нулевым | признак = `0.0` |
| **insufficient** — сыграла мало | `NaN`/значение + счётчик наблюдений |

Модель использует `SimpleImputer(0.0)`, то есть `NaN` станет нулём.
Поэтому **счётчики подаются отдельно** (`recent_n_min_*`,
`common_opponent_count`, `h2h_matches_decayed`): без них «нет данных» и
«ноль перформанса» неразличимы. Тест 7 проверяет, что различие
сохраняется.

Reliability-канал вводится **только** там, где механизм его требует, и
не копируется из H1 автоматически (§15).

```
M0 = B0                    фактический frozen pre-match
```

## 6. Критерии решения

| Вердикт | Условие |
|---|---|
| **KEEP** | Δlog loss > 1e-4 на VAL **поверх B2**, устойчиво по годам, подтверждено на TEST |
| **CONDITIONAL** | работает только в подгруппе (например ≥5 общих соперников) — фиксируется как условный механизм, **не** становится глобальным признаком (§32) |
| **REDUNDANT** | коррелирует с исходом, но не улучшает базу |
| **REMOVE** | не проходит порог |
| **NOT TESTABLE** | данных не существует |

**Фаза не обязана закончиться KEEP.** Если ни один механизм не даёт
независимой информации — это результат, и он означает, что feature
engineering на pre-match слое исчерпан и пора к Draft Model (§32).

## 7. Границы (§1, §26)

Запрещено и не используется: picks, bans, драфт, hero-player,
Team×Hero, Player×Hero, post-match `lane_role`, любые данные, известные
только после начала матча. Все признаки существуют в `PREDICT(T)`.

Не меняются: frozen model, калибровка, KEEP-признаки, формула H1.

Не делается: перебор десятков окон, десятки interaction-признаков,
подгонка под Spirit vs VISION, оптимизация по TEST.
