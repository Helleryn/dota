# Research Summary — итог Phase 2 + Phase 3

Дата: 2026-08-24. Статус фактов: `VERIFIED` / `INFERRED` / `REQUIRES LIVE VERIFICATION`
(см. `docs/data-sources.md` и `docs/data-feasibility.md` для полного контекста).

## 1. Какой dataset реально можем построить?

Датасет "одна строка = один профессиональный матч" на основе **OpenDota как
единственного источника для MVP**: `match_id`, `start_time`, `patch`,
`leagueid`/`tier`, `radiant_team_id`/`dire_team_id`, `radiant_win`, плюс
производные признаки (Elo, форма, patch-статистика), пересчитанные нами самими
walk-forward из истории матчей команд. Полная схема — `docs/data-feasibility.md`
(раздел "MVP dataset: обоснование").

Точный объём (сколько именно матчей, за какой точный период) — `REQUIRES LIVE
VERIFICATION`, см. пункт 5 и `scripts/verify_data_source.py`.

## 2. Какой минимальный dataset нужен для baseline?

`team_elo` (собственный, walk-forward) + `recent_winrate_10` — это Feature Set 0
(`docs/features.md`). Механизм Elo проверен на синтетических данных
(`scripts/elo_prototype.py`) и подтверждённо не содержит утечки из будущего.

## 3. Какой источник является основным?

**OpenDota.** Обоснование (`VERIFIED` фактами из чтения исходников `odota/core`):
официально документированный REST API, бесплатный без ключа (60 req/min),
эндпоинт `/explorer` с произвольным SQL резко упрощает построение агрегатов
(историческая глубина проверяется ОДНИМ запросом вместо сотен), уже
фильтрует про-матчи по `tier IN (premium, professional)`, отдаёт структуру
драфта и посекундные данные игроков.

## 4. Какие fallback source?

- **STRATZ** — та же телеметрия матчей другим API (GraphQL), на случай
  недоступности OpenDota. Не задействован в MVP, чтобы не удваивать
  зависимость раньше времени.
- **Liquipedia** — НЕ fallback, а дополняющий источник: официальная история
  составов/трансферов и структура турнирных сеток (group/playoff/bracket),
  которых в OpenDota структурированно нет. Используется начиная с Feature
  Set 1-3, не в Set 0.
- **datdota** — только как ручной QA-инструмент для сверки "что считается
  профессиональным матчем", не как программный источник (публичный API не
  подтверждён — `REQUIRES LIVE VERIFICATION`).

## 5. Какой исторический период используем?

Не зафиксирован окончательно — по правилу проекта, цифры не выдумываются.
Гипотеза (`INFERRED`): приемлемое покрытие примерно с 2015–2017, наилучшее —
с 2018 (эра DPC). Точная граница и объём по годам — `REQUIRES LIVE
VERIFICATION` через `scripts/verify_data_source.py` (агрегирующий запрос к
`/explorer`, группировка по годам). Финальное решение о train/val/test
периодах откладывается до получения этого отчёта — фиксироваться будет в
`docs/backtesting.md` на Phase 4+.

## 6. Какие features будут в MVP?

Feature Set 0-1 из `docs/features.md`: `team_elo`, `recent_winrate_5/10/20`,
`recent_form_ema`, `team_winrate_on_current_patch`, `team_matches_on_current_patch`,
`league_tier`, `bo_type` (кодировка требует верификации), `h2h_winrate_alltime`
с gating по `h2h_matches_count`.

## 7. Какие features отложены?

- Roster-признаки (Feature Set 2) — реализация валидна и спроектирована, но
  требует либо реконструкции ростера из истории матчей (нетривиальный, но
  посильный код), либо интеграции с Liquipedia (rate-limited) — отложено до
  подтверждения, что MVP на Set 0-1 вообще работает лучше baseline.
- Player-level признаки (часть Set 2/3) — данные доступны (`player_matches`),
  но требуют отдельного слоя role/hero-агрегации.
- Bracket/tournament stage (Set 3) — зависит от интеграции Liquipedia.
- Весь draft-aware блок (Set 4, категория H.2 из `docs/features.md`) —
  архитектурно предусмотрен, но это отдельный режим прогноза
  ("после драфта"), не часть pre-match MVP.

## 8. Какие features опасны из-за leakage?

Полный разбор — `docs/data-leakage.md`. Коротко, зоны наибольшего риска:

- **Готовый `team_rating` OpenDota** как прямая замена собственного Elo —
  это снэпшот "на сегодня", не point-in-time история → решено не
  использовать напрямую, пересчитывать самим.
- **"Текущий" ростер команды** через `/teams/{id}/players` — тот же
  снэпшот-риск, `VERIFIED` по коду эндпоинта.
- **Draft-производные признаки** (`picks_avg_patch_winrate` и т.п.) в
  pre-match контексте — недоступны физически до начала драфта, должны быть
  жёстко изолированы в отдельный набор колонок/датасет.
- **`is_elimination_match`**, если вывести из результата матча вместо
  структуры турнирной сетки — тавтологическая утечка.

## 9. Как будем делать time-based validation?

Финальная схема — предмет Phase 4 (architecture) после получения реальных
цифр покрытия по годам (пункт 5). Рабочая гипотеза на основе задания и
объёма данных, которую предстоит подтвердить: walk-forward / rolling-схема
(а не единственный фиксированный train/val/test срез), т.к. это точнее
имитирует продовый режим работы (модель никогда не видит будущее
относительно момента прогноза) и даёт больше test-точек для оценки
стабильности качества по времени, чем один статичный сплит. Простой
`train_test_split` со случайным перемешиванием исключён категорически
(прямое требование задания и логика Elo/roster-признаков, которые сами по
себе последовательны во времени).

## 10. Как будем делать backtesting?

Концептуально (детализация — `docs/backtesting.md`, Phase 4+): идти по
матчам в хронологическом порядке, для каждого матча признаки строятся
исключительно из данных до его `start_time` (тот же принцип, что уже
реализован и проверен в `scripts/elo_prototype.py` для Elo — будет
обобщён на весь набор признаков), прогноз сравнивается с фактом, накопленные
метрики считаются на растущем test-окне.

## 11. Какие модели будем сравнивать?

Список из задания принимается как отправная точка, без предрешения
результата: random baseline, "всегда сильнее по Elo", логистическая
регрессия, Random Forest, CatBoost/LightGBM/XGBoost. Явный критерий (из
задания, раздел 8): сложная модель оправдана, только если она статистически
значимо превосходит простой Elo/логрег baseline на held-out данных — иначе
использовать более простую модель.

## 12. Как будем измерять качество?

Log Loss и Brier Score — основные метрики (задание явно требует вероятностную
калибровку, не только accuracy), плюс ROC-AUC, precision/recall/F1,
calibration curve. Обязательна проверка статистической значимости прироста
между моделями/feature sets (не полагаться на "0.5% accuracy выше" без
доверительного интервала) — детали в `docs/evaluation.md` (Phase 8+).

## 13. Какие неизвестные ещё нужно проверить через реальный API?

Явный список `REQUIRES LIVE VERIFICATION` (запускается через
`scripts/verify_data_source.py` пользователем вне текущей среды):

1. Реальный объём про-матчей (`tier IN premium, professional`) по годам —
   агрегирующий SQL-запрос уже встроен в скрипт.
2. Точная кодировка `series_type` (0/1/2 → Bo1/Bo3/Bo5) — сверить с известными
   Bo5-финалами.
3. Актуальные rate limit заголовки ответа (документация могла устареть).
4. Полнота `picks_bans` — доля про-матчей, где это поле реально заполнено.
5. STRATZ Default-token лимиты — подтверждены только веб-поиском
   (`docs/data-sources.md`), не прямым запросом.
6. Публичный API-контракт datdota — существует ли он в задокументированном
   виде вообще.

## 14. Что делать следующим этапом?

Предлагается **Phase 4 — Architecture**: база данных (`docs/database-design.md`
с ER-диаграммой в Mermaid), архитектура data pipeline (Raw → Normalized →
Feature → Dataset, уже намеченная в `docs/data-feasibility.md`, детализировать
до конкретных таблиц/файлов), архитектура ML pipeline, набросок API,
технологический стек с обоснованием выбора (не по умолчанию из задания, а
через сравнение альтернатив). До начала Phase 4 — дождаться результата
пункта 13 (реальные цифры покрытия), т.к. они влияют на решение по
train/val/test схеме (пункт 9), которая, в свою очередь, — часть
архитектуры.

## Addendum после Phase 4 (архитектура)

Пользователь явно указал не блокировать разработку сетевыми ограничениями
(п.13 выше остаётся `REQUIRES LIVE VERIFICATION`, но Phase 4 спроектирована
так, чтобы не зависеть от точных цифр — см. `docs/architecture.md`, раздел 1
и `src/config.py`, где границы данных — параметры, а не константы).

Архитектура Phase 4 **подтвердила**, а не изменила, выводы Phase 2-3:
OpenDota остаётся основным источником (формализовано в ADR-001), собственный
walk-forward Elo — в ADR-003 (реализован как переиспользуемый компонент
`RatingEngine` в `src/ratings/engine.py`, используется идентично в training/
backtesting/serving), walk-forward валидация без random split — в ADR-005.
Дополнительно приняты: PostgreSQL с JSONB для raw-слоя без object storage на
MVP (ADR-002), scikit-learn + CatBoost как ML-стек (ADR-004).

Ничего из выводов Phase 2-3 не пересмотрено — Phase 4 добавила схему БД
(`docs/database-design.md`), стратегию identity resolution
(`docs/team-identity.md`, ранее не проработанную детально), дизайн pipeline
(`docs/data-pipeline.md`) и API (`docs/api.md`), не изменив базовых
решений. Полный список открытых вопросов для `scripts/verify_data_source.py`
(п.13) остаётся актуальным без изменений.
