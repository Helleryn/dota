# PHASE 17 — состав на момент прогноза

---

## 1. Три уровня знания (PART D/J)

| Уровень | Что известно | Что делает система |
|---|---|---|
| `KNOWN_ROSTER` | все пять игроков | признаки состава считаются |
| `PARTIAL_ROSTER` | часть пятёрки | считаются по известным, число известных сохраняется |
| `UNKNOWN_ROSTER` | ничего | признаки состава = **None**, не значения по умолчанию |

Прямой запрет фазы выполнен: **при неизвестном составе сегодняшний
состав не подставляется.** `RosterProvider.for_match` возвращает пустое
множество, а не «последний известный».

Проверено: `test_unknown_roster_yields_none_not_defaults`,
`test_partial_roster_is_not_silently_completed`,
`test_todays_roster_is_not_used_for_yesterday`.

## 2. Player-Elo привязан к игроку, а не к team_id

Сценарий из задания проверен напрямую:

```
Команда 100: игроки {1,2,3,4,5}, 20 матчей, все победы
Игрок 1 уходит в команду 300 с новыми партнёрами {21..24}
Команда 100 берёт замену: {2,3,4,5,25}
```

Результат: рейтинг игрока 1 уходит **вместе с ним**; новичок 999
получает базовые 1000, а не чужую историю.

Тесты: `test_player_elo_follows_the_player_not_the_team`,
`test_team_identity_does_not_transfer_rating_between_people`.

Это свойство движка по построению: `player_elo` — словарь по
`account_id`, `team_id` в нём не участвует.

## 3. Что стоит отсутствие состава (VALIDATION, горизонт 0)

| Переход | Δaccuracy | ΔROC-AUC | Δlog loss |
|---|---:|---:|---:|
| T0 → T1 (**нет драфта**) | −0.0039 | −0.0061 | +0.0026 |
| T1 → T2 (**нет состава**) | **−0.0174** | **−0.0293** | +0.0149 |
| T0 → T2 (нет ни того, ни другого) | −0.0213 | −0.0354 | — |

> **Гипотеза P3 подтверждена: потеря состава стоит вчетверо дороже
> потери драфта.**

Это согласуется со всей линией Phase 9–13: сигнал живёт в player-Elo, а
не в героях. И это меняет приоритеты для продукта: искать надо источник
составов, а не источник драфта.

## 4. Что делать при неизвестном составе (PART J)

Сравнение двух стратегий на VALIDATION, горизонт 24 ч:

| Доля матчей без состава | Подстановка нулей (acc / ll) | Переход на модель T2 (acc / ll) |
|---:|---|---|
| 0% | 0.5979 / 0.6578 | 0.5979 / 0.6578 |
| 25% | 0.5936 / 0.6623 | 0.5941 / **0.6614** |
| 50% | 0.5890 / 0.6674 | 0.5882 / **0.6658** |
| 77.5% | 0.5841 / 0.6721 | 0.5846 / **0.6695** |
| 100% | 0.5784 / 0.6775 | 0.5788 / **0.6739** |

**Гипотеза P4 подтверждена, но слабо.** Переход на модель без состава
даёт систематически лучший log loss (на 0.0036 при полном отсутствии
составов), accuracy при этом практически не отличается.

Вывод для продукта: переключаться на T2, а не подставлять нули. Выигрыш
скромный, но он в правильной метрике — качество вероятностей, а не
дискриминация. И он честнее: подстановка нуля означает «разница в силе
пятёрок ровно нулевая», что является утверждением, а не отсутствием
знания.

Доля 77.5% выбрана не случайно: столько предстоящих матчей не имеют
состава по замеру Phase 16.

## 5. Ограничение, которое остаётся

Для исторического replay состав берётся из `match_players` — это
**фактический** состав, то есть post-match величина. Соглашение принято
в Phase 7/8 и здесь не пересматривается.

Phase 17 не делает вид, что это pre-match знание: провайдер составов
передаётся отдельным аргументом и может быть отключён. Именно это
позволило измерить уровень T2 — то, что реально доступно, когда состава
нет.
