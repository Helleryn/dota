# PHASE 18 — источники pre-match данных: что доступно на самом деле

> Всё ниже — результаты **запросов**, а не чтения документации. Phase 16
> объявила правило «документация не является доказательством» и сама же
> его нарушила: её главный вывод оказался измерением другой игры.

---

## 1. Ошибка Phase 16 и её исправление

Phase 16 сообщила: «bo3.gg — 378 предстоящих матчей Dota, медиана запаса
94.8 ч, полный состав у 10.1%».

**Это были матчи Counter-Strike 2.** В bo3.gg `discipline_id=1` — CS2,
Dota 2 — `discipline_id=4`. Проверено запросом `/disciplines`:
`[(1,'Counter-Strike 2'), (2,'Valorant'), (3,'League of Legends'),
(4,'Dota 2'), …]`.

Обнаружено не проверкой кода, а взглядом на данные: в матче tier=s
оказались FalleN, YEKINDAR и yuurih — состав FURIA по CS2. Ни один тест
этого не ловил, потому что тесты проверяли форму ответа, а не то, про
какую игру ответ.

| Величина | Phase 16 (CS2) | **Phase 18 (Dota 2)** |
|---|---:|---:|
| предстоящих матчей | 378 | **15** |
| медиана запаса | 94.8 ч | **49.3 ч** |
| известны за ≥24 ч | 82.3 % | **100 %** |
| известны за ≥7 суток | 30.4 % | **0 %** |
| полный состав (10 игроков) | 10.1 % | **46.7 %** |

Расписание оказалось **вчетверо хуже**, составы — **вчетверо лучше**.
Оба вывода Phase 16 о bo3.gg заменены.

**Урок, вынесенный в правило:** проверка источника обязана включать
проверку *предметной области*, а не только доступности и формата. В
живом конвейере это теперь константа `DOTA_DISCIPLINE = 4` рядом с
комментарием о том, чем она была раньше.

## 2. Карта источников по результатам запросов

| Источник | Расписание | Составы | Роли | Патч | Пригодность |
|---|---|---|---|---|---|
| **bo3.gg** (`discipline_id=4`) | **да**, 15 матчей | **да**, ники | `role=None` **у всех** | нет | основной источник расписания и составов |
| **Valve DPC** | да, 41 матч | нет | нет | нет | бесполезен: все лиги tier `excluded` |
| **OpenDota** | **нет** | реестр `proPlayers` | нет | `/constants/patch` | реестр идентичностей + история матчей |
| **Liquipedia** | да (вики) | да, с датами | да | да | парсер написан (Phase 16), но ToS ограничивает автоматический доступ |

### 2.1 Почему Valve DPC не работает

Измерено, а не предположено:

* обе лиги, публикующие расписание, имеют tier **`excluded`**;
* лига 19081 (36 из 41 будущих матчей) имеет в OpenDota **0 матчей**;
* все её команды имеют **0 матчей** в OpenDota при **любом** tier;
* **ни одна из 15 лиг нашего домена**, активных за 90 дней, не публикует
  будущих матчей в Valve DPC.

Это, а не ошибка кода, объясняет `ABSTAIN = 38` в live shadow Phase 17.

### 2.2 Чего нет ни в одном источнике

| Факт | Статус |
|---|---|
| **роль игрока на конкретный матч** | источника не существует; у bo3.gg поле `role` равно `None` у всех 133 игроков |
| **заявленный стартовый состав** | не публикуется; составы у bo3.gg — это состав *команды*, а не заявка на матч |
| расписание за ≥7 суток | 0 % матчей |

Отсутствие роли — не пробел в реализации, а **свойство предметной
области**. Phase 11 уже показала, что post-match `lane_role` из реплея
использовать нельзя; Phase 18 добавляет, что pre-match источника роли
тоже нет. Признаки роли закрыты окончательно.

## 3. Сопоставление идентичностей

Названия команд для связывания **не используются нигде**: Phase 10
нашла 461 пару `team_id` с одинаковым именем, существовавших
параллельно.

Работающий способ — **по игрокам**, через реестр `proPlayers` OpenDota:

| | |
|---|---:|
| игроков в предстоящих матчах | 133 |
| сопоставлено однозначно | **88 (66.2 %)** |
| из них есть в нашей базе | **88 (100 %)** |
| неоднозначных ников | 17 |
| матчей с полными 10 игроками | **0** (лучший — 9/10) |

Нормализация ника — NFKD + нижний регистр + только буквы и цифры.
Неоднозначность (`len(candidates) != 1`) **не разрешается произвольным
выбором**: игрок пропускается.

Отсюда главный вывод фазы о данных: **рабочий режим — частичный
состав.** Полного состава не бывает никогда.

---

## 4. Ограничение, которое вносит сам этот метод

Реестр `proPlayers` — **снимок «сегодня»**. Для живого прогноза (T =
сейчас) это законно. Для **исторического** replay запрещено: применять
сегодняшнее соответствие «ник → account_id» к прогнозу годичной
давности значит протаскивать сегодняшнее знание в прошлое.

В историческом конвейере (`src/pit/`) реестр не используется.
Ограничение внесено в карту рисков утечки как новое для проекта.
