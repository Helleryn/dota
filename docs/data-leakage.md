# Data Leakage Audit

## Главный принцип

> Любой признак матча `m`, начинающегося в момент `start_time(m)`, обязан
> вычисляться ТОЛЬКО из данных с фактическим моментом появления (`available_at`)
> строго раньше `start_time(m)`.

Это касается не только "очевидных" вещей вроде итогового счёта, но и куда более
коварных случаев: агрегатов, которые незаметно включают сам предсказываемый
матч, "текущих" срезов состояния (ростер/рейтинг "на сегодня" вместо "на дату
матча"), и артефактов сбора данных (когда матч физически ЗАПИСАН в БД позже,
чем он начался — момент записи ≠ момент начала).

## Общий чеклист против утечки (применять к каждому новому признаку)

1. **Temporal cutoff.** Любая агрегация ("win rate", "среднее", "count") обязана
   иметь явный фильтр `WHERE start_time < t`, где `t` — момент предсказываемого
   матча, а не "текущая дата выполнения запроса" и не "весь датасет".
2. **Исключение самого матча.** При join'е признаков к таблице матчей — leaky
   join включает сам `match_id`, для которого считается признак (например,
   "team win rate" по неосторожности посчитан по всем матчам команды,
   включая тот, что мы пытаемся предсказать).
3. **Point-in-time состояние, а не текущий снэпшот.** "Текущий" ростер, "текущий"
   Elo, "текущий" топ-20 команд — всегда должны означать "на дату `t`", а не
   "на сегодня" (день выполнения ML-пайплайна). Использование сегодняшнего
   состояния — самая частая и самая незаметная ошибка в спортивной аналитике.
4. **Момент появления данных ≠ момент события.** Например, официальное
   объявление о смене состава может появиться на Liquipedia через несколько
   дней после фактической игры первого матча новым составом — если
   использовать `changed_at` из Liquipedia без сверки с фактическими датами
   матчей, можно случайно узнать о смене раньше, чем она была публично
   известна.
5. **Идентичность команды не должна "знать будущее".** Если команда сменила
   название/организацию после матча `m`, признаки для `m` обязаны
   использовать историю под старым именем/tag на момент `m`, не текущее.
6. **Проверка на синтетическом контрпримере.** Для каждого стейтфул-признака
   (Elo, форма, ростер) — построить тест по образцу
   `scripts/elo_prototype.py::assert_leakage_safe`: pre-match значение признака
   должно точно совпадать с независимым пересчётом только по более ранним
   данным.

## Аудит по группам признаков

### Elo / team strength

**Риск:** высокий, если рейтинг берётся из готового внешнего сервиса как
"текущее" значение вместо пересчёта. **Статус решения — см. отдельный раздел
ниже.**

- Наивная (ошибочная) реализация: `SELECT rating FROM team_rating WHERE team_id = X`
  прямо перед матчем — это ТЕКУЩИЙ рейтинг команды в БД OpenDota на момент
  запроса, который уже включает все матчи вплоть до сегодняшнего дня, в том
  числе более поздние, чем `m`, если запрос идёт офлайн по историческим данным
  задним числом (например, при построении train-датасета за 2023 год в 2026
  году). Это классическая утечка "рейтинг из будущего".
- Правильная реализация: пересчитать Elo walk-forward по всей истории матчей,
  беря pre-match значение строго на момент каждого матча (см. `scripts/elo_prototype.py`).

### Recent form (recent_winrate_N, EMA)

**Риск:** средний, источник ошибки — неправильные границы окна.

- Наивная ошибка: `ORDER BY start_time DESC LIMIT N` без условия
  `WHERE start_time < t` — если случайно взять N *ближайших по индексу*
  матчей без сортировки по времени относительно `t`, можно включить более
  поздние игры (актуально при параллельной обработке батчами без явной
  сортировки).
- Правильная реализация: строго `WHERE start_time < t ORDER BY start_time DESC LIMIT N`,
  выполняется в хронологическом проходе по данным команды (аналогично Elo).

### Player statistics

**Риск:** средний.

- Наивная ошибка: усреднение "личной результативности" игрока по ВСЕМ его
  матчам без разделения по времени — включает будущие матчи (в том числе
  за другие команды, что дополнительно смешивает контекст).
- Правильная реализация: только матчи игрока с `start_time < t`, и — отдельный
  нюанс — только за период, когда игрок действительно состоял в оцениваемой
  команде (иначе результативность в другой команде "просачивается" как
  характеристика текущей).

### Roster (состав команды)

**Риск: самый высокий из всех групп**, отдельно подчёркнут в задании.

- Наивная ошибка №1: "текущий состав команды" определяется по последнему
  известному на сегодня ростеру (например, из `/teams/{id}/players`, который
  — `VERIFIED` — является ALL-TIME агрегатом, не point-in-time срезом). Это
  прямая утечка: используется состав, сформированный уже ПОСЛЕ предсказываемого
  матча.
- Наивная ошибка №2 (тоньше): "матчей текущим составом" считается по составу,
  который сыграл в матче `m` — то есть по факту РЕЗУЛЬТАТА, который мы и
  пытаемся предсказать. Это тавтологическая утечка: признак строится из
  информации, ставшей известной только в момент старта самого матча
  (заявленный lineup), что для *обучения* допустимо (лайнап объявляется до
  игры), но для *продового инференса* требует отдельного источника — анонса
  состава, а не постфактум результата.
- Правильная реализация: `roster_matches_played(t)` = число матчей команды,
  сыгранных ДО `t`, в которых состав идентичен составу, заявленному НА матч
  `m` (а состав на матч `m` в проде должен приходить из lineup announcement,
  на train — можно использовать фактический состав матча `m`, т.к. он и есть
  "анонс" в историческом смысле, при условии, что признак не использует
  РЕЗУЛЬТАТ матча `m`, только состав).

### Patch statistics

**Риск:** низкий для самого `patch` (он логически не может быть "из будущего"
для матча, который на нём же прошёл), средний — для агрегатов вида
`win_rate_on_current_patch`.

- Наивная ошибка: `win_rate_on_current_patch` считается по всем матчам
  команды на этом патче, включая сам матч `m` (типичная off-by-one ошибка —
  забыли исключить текущую строку при `GROUP BY patch`).
- Правильная реализация: тот же temporal cutoff `start_time < t`, дополнительно
  отфильтрованный по `patch = patch(t)`.

### Hero statistics (для draft-aware режима)

**Риск:** высокий, но иного рода — не "из будущего по времени", а
"недоступно до наступления события внутри этого же матча".

- Наивная ошибка: использовать `hero_winrate_on_patch(picked_hero)` в
  pre-match (до драфта) датасете — герои матча `m` физически не выбраны до
  начала драфта, этот признак не может существовать в pre-match контексте.
  Это не "утечка из будущего матча", а "утечка из будущей стадии этого же
  матча" — тип ошибки, специфичный именно для двухфазной архитектуры
  pre-match/draft-aware (см. `docs/features.md`, H.1 vs H.2).
- Правильная реализация: строгое архитектурное разделение — pre-match модель
  физически не имеет доступа к колонкам `picks_bans`-производных признаков;
  они существуют только в отдельном draft-aware датасете/наборе колонок.

### Head-to-head

**Риск:** низкий по времени (легко соблюсти temporal cutoff), но высокий риск
**переобучения/переоценки значимости** признака при малом числе очных встреч
— задание прямо предупреждает не переоценивать h2h.

- Наивная ошибка: использовать `h2h_winrate` без учёта `h2h_matches_count` —
  при 1 очной встрече `h2h_winrate` равен 0 или 1, что модель может
  интерпретировать как сильный сигнал, хотя это шум.
- Правильная реализация: gating по `h2h_matches_count` (см. `docs/features.md`,
  категория F) — при малом числе встреч признак должен быть NaN, а не
  экстремальным значением.

### Tournament statistics (bracket/stage, tier)

**Риск:** низкий — эти данные по своей природе известны заранее (турнирная
сетка объявляется до начала матчей), но есть нюанс с bracket-позицией.

- Наивная ошибка: помечать матч как "elimination match" на основе того,
  что случилось ПОСЛЕ него (например, "эта команда вылетела" узнаётся только
  по факту поражения в этом самом матче — это тавтология, если "elimination"
  выводится из результата, а не из турнирной сетки).
- Правильная реализация: `is_elimination_match` должен определяться ИСКЛЮЧИТЕЛЬНО
  структурой турнирной сетки (это single-elimination слот в bracket), не
  результатом самого матча.

## ELO: собственный расчёт vs готовый рейтинг OpenDota

Три рассмотренных варианта:

1. **Использовать готовый `team_rating` OpenDota как есть.** Отклонено.
   Причина — `VERIFIED` факт: это текущий снэпшот (одна строка на команду,
   без истории), обновляемый только для новых матчей по мере их появления в
   БД OpenDota. У API нет эндпоинта "рейтинг команды X на дату Y" — то есть
   технически невозможно получить point-in-time значение без пересчёта, а
   использование текущего значения для исторических матчей — прямая утечка
   (см. пример выше).
2. **Использовать несколько готовых рейтингов одновременно (OpenDota Elo +
   STRATZ, если есть аналог).** Отклонено для MVP по той же причине (снэпшот,
   не история) и по причине лишней зависимости от второго внешнего сервиса
   без явной выгоды, пока не пересчитан собственный рейтинг.
3. **Пересчитывать собственный Elo walk-forward.** **Выбрано.** Формула
   идентична проверенной в исходном коде OpenDota (K=32, база 1000,
   стандартная логистическая ожидаемая вероятность), но пересчитывается нами
   по всей истории матчей в хронологическом порядке, что даёт полный контроль
   над:
   - **historical state** — pre-match значение на любую историческую дату,
     не только "сегодня";
   - **update timestamp** — обновление ratings происходит атомарно вместе с
     обработкой каждого матча в pipeline, а не асинхронно сторонним сервисом;
   - **K-factor** — можно экспериментировать (напр., увеличенный K для первых
     матчей команды/нового состава — "быстрая калибровка", по аналогии с
     Glicko rating deviation) без форка чужого сервиса;
   - **инициализация** — явно решить, что делать с новыми командами (база
     1000) и с "новым составом старой команды" (см. ниже — открытый вопрос);
   - **decay** — при желании добавить затухание рейтинга при долгом простое
     команды (не реализовано в OpenDota-версии) — гипотеза для Feature Set 1+;
   - **opponent strength** — расчёт уже учитывает силу оппонента по
     построению (это свойство Elo), но собственная реализация позволяет
     дополнительно логировать `expected_win_probability` как отдельный
     признак (не только итоговый рейтинг).

   Работоспособность механизма подтверждена прототипом `scripts/elo_prototype.py`
   на синтетических данных: `assert_leakage_safe()` проверяет, что pre-match
   рейтинг любого матча точно равен независимому пересчёту только по более
   ранним матчам — прогон подтвердил отсутствие утечки на 12 синтетических
   матчах.

**Открытый вопрос (для Phase 4/7, не решается здесь):** должен ли Elo
"сбрасываться" или частично затухать при значительной смене состава команды
(например, взвешенный перенос части рейтинга на новый состав)? Это отдельная
исследовательская гипотеза, пересекающаяся с группой признаков Roster —
затухание Elo при смене состава может дублировать сигнал `days_since_roster_change`,
и наоборот, отсутствие затухания может занижать ценность roster-признаков.
Решать эмпирически в Phase 7 (Feature Set 0 vs Set 2 comparison), не
постулировать сейчас.

## Missing data — общий принцип

Отсутствие данных **не должно** молча превращаться в "нейтральное" значение
(0.5 для winrate, среднее по датасету и т.п.) без явного флага, потому что
само по себе отсутствие истории часто коррелирует с исходом (например, дебют
команды на про-сцене — это не "нейтральная" ситуация, а высокая
неопределённость). Каждый признак в `docs/features.md` со стратегией
"NaN + флаг" обязан сопровождаться отдельным бинарным признаком
`<feature>_is_missing` / `insufficient_history`, который сама модель (или explicit
imputation стратегия) может использовать, чтобы не путать "низкое значение"
с "неизвестное значение".
