# PHASE 2 — Data Feasibility

Статус: 2026-08-24. Маркировка каждого факта:

- `VERIFIED` — подтверждено чтением исходного кода/схемы `odota/core` или реального примера ответа API.
- `INFERRED` — логический вывод из документации/исходников/общеизвестной практики, но не подтверждён напрямую живым запросом.
- `REQUIRES LIVE VERIFICATION` — нужен реальный HTTP-запрос из среды с доступом в интернет; см. `scripts/verify_data_source.py`.

Ключевой вопрос этой фазы не "что существует", а:

> Какой dataset мы реально сможем регулярно строить и обновлять?

## MVP dataset: обоснование

Задание предлагает пример `matches + teams + players + rosters + heroes + patches + picks/bans + tournaments`, но бездумно копировать его нельзя — нужно обосновать, что из этого действительно необходимо для **первой, простой, но надёжной модели**.

Требование пользователя явное: первая модель должна работать **без** live-драфта, без сложной player-level аналитики, без платных API и без сложного scraping. Это отсекает Категории 2–4 из MVP. Остаётся Категория 1 плюс минимально необходимая агрегация:

```text
MVP dataset (одна строка = один сыгранный матч):

match_id, start_time, patch, leagueid/tier, bo_type(?)
radiant_team_id, dire_team_id, radiant_win

# производные (считаются из истории ДО этого матча, не хранятся "сырыми"):
team_a_elo_pre_match, team_b_elo_pre_match
team_a_recent_winrate_N, team_b_recent_winrate_N   (N = 5/10/20)
team_a_matches_on_patch, team_b_matches_on_patch
```

Обоснование каждого элемента:

- **`match_id` + `radiant_win`** — обязательный минимум: без целевой переменной обучать нечего.
- **`radiant_team_id`/`dire_team_id`** — без идентификации команд невозможно построить team-level рейтинг.
- **`patch`** — Dota 2 регулярно и существенно меняет баланс; смешивать матчи разных патчей в one bag без учёта патча — заведомо terrible baseline (задание прямо требует patch-aware моделирование).
- **`leagueid`/`tier`** — нужен как фильтр качества (не пускать в датасет случайные амateur-лиги, которые размывают сигнал) и потенциально как грубый прокси "уровня турнира" уже в MVP.
- **Elo (team_a/b)** — компактно кодирует всю прошлую историю силы команды одним числом, дёшево считается, дёшево обновляется, интерпретируем.
- **Recent winrate** — Elo медленно реагирует на резкие изменения (смена состава, всплеск формы); recent form — недорогой комплемент.

Что **осознанно исключено из MVP**, хотя фигурирует в примере задания:

- **`players`/`rosters` как отдельные первоклассные сущности** — не потому что не нужны вообще, а потому что: (а) сами по себе они не признак, а источник для будущих признаков (hero pool, individual rating), которые относятся к Feature Set 2, не Feature Set 0; (б) MVP explicitly не должен зависеть от player-level аналитики.
- **`picks_bans`** — по определению доступны только после начала драфта; MVP — это pre-match (до драфта) прогноз.
- **`heroes`/`hero_stats`** — нужны только для draft-aware режима (Feature Set 4).
- **`tournaments` как отдельная сущность с bracket/stage** — MVP использует только `leagueid`/`tier` (уже есть в OpenDota); полноценный bracket/stage из Liquipedia — это Категория 2, добавляется в Feature Set 1.

Итог: MVP-датасет целиком строится из **одного источника (OpenDota)**, без Liquipedia/STRATZ/scraping — это резко снижает операционный риск первого прогона пайплайна.

## PHASE 2.1 — Data coverage (историческое покрытие)

Прямая проверка невозможна из этой среды (см. `docs/environment-constraints.md`) — сетевой доступ к `api.opendota.com` заблокирован политикой текущего окружения. Ничего не придумываю, фиксирую факт честно:

| Период | Статус | Основание |
|---|---|---|
| 2011–2014 | `INFERRED`, вероятно фрагментарно | Ранняя эра Dota 2 esports, tier-система лиг в современном виде ещё не устоялась; team identity особенно неоднозначна (см. Категория 4) |
| 2015–2017 | `INFERRED`, вероятно приемлемо | Возникновение современной структуры мейджоров/DPC-предшественников совпадает с ростом покрытия tier-лиг |
| 2018–2022 | `INFERRED`, вероятно хорошее | DPC-эра, стандартизированная система лиг |
| 2023–2026 | `INFERRED`, вероятно наилучшее | Текущая DPC-структура, активное сообщество разработки OpenDota |

Все строки этой таблицы — гипотеза, требующая `REQUIRES LIVE VERIFICATION`. Для этого создан `scripts/verify_data_source.py` (см. ниже) — пользователь должен запустить его в среде с доступом к интернету и вернуть результат, прежде чем финально фиксировать период train/val/test в `docs/backtesting.md` (Phase 4+).

## PHASE 2.2 — Source abstraction (концепция)

Архитектура **не должна быть жёстко привязана к OpenDota**. Причины: (1) OpenDota — некоммерческий проект на добровольных началах, доступность не гарантирована контрактом; (2) часть данных (roster history, bracket/stage) в принципе не из OpenDota, а из Liquipedia — нужен единый интерфейс для разнородных источников; (3) смена источника не должна требовать переписывания feature engineering и downstream-кода.

Концепция:

```text
                 ┌─────────────────────┐
                 │     DataSource       │   абстрактный интерфейс
                 │  (protocol/ABC)      │
                 └──────────┬───────────┘
                             │
        ┌────────────────────┼─────────────────────┐
        │                    │                      │
┌───────▼────────┐  ┌────────▼─────────┐  ┌─────────▼──────────┐
│ OpenDotaSource   │  │ LiquipediaSource  │  │ StratzSource        │
│ (matches, draft,  │  │ (rosters,         │  │ (запасной источник  │
│  team_rating,     │  │  tournaments,     │  │  той же телеметрии, │
│  heroes, patches) │  │  bracket/stage)   │  │  если OpenDota      │
│                    │  │                    │  │  недоступен)         │
└────────────────────┘  └────────────────────┘  └──────────────────────┘
```

Каждый `*Source` реализует единый набор методов с одинаковой сигнатурой (например, `fetch_matches(since, until) -> Iterable[RawMatch]`, `fetch_team_roster_history(team_id) -> Iterable[RosterChange]`), возвращающих **общие типизированные структуры** (не сырые dict конкретного API) — это и есть точка развязки. Downstream-код (Raw→Normalized слой, см. Phase 2.3) работает только с этими общими структурами и не знает, откуда они получены.

Минимальный интерфейс без реализации сетевой логики зафиксирован в `src/datasources/base.py` — это иллюстрация концепции (Protocol/ABC + dataclasses), не production-клиент. Реальные HTTP-клиенты пишутся в Phase 5.

## PHASE 2.3 — Raw / Normalized / Feature / Dataset

```text
RAW DATA           — точная копия ответа источника (JSON as-is) + metadata:
                      {source, fetched_at, source_url/query, raw_payload}
      ↓
NORMALIZED DATA     — приведено к единой внутренней схеме (см. DataSource
                      abstraction выше), team identity разрешена
                      (organization/team/roster разделены — см. Категория 4),
                      единицы измерения и типы унифицированы
      ↓
FEATURE DATA        — точечные во времени (point-in-time) агрегаты:
                      team_elo_at(match_id), recent_winrate_at(match_id, n)
                      и т.д. Каждая запись имеет явный `as_of_timestamp`
      ↓
ML DATASET          — одна строка на матч, только признаки, известные
                      строго до `start_time` этого матча + целевая
                      переменная `radiant_win`
```

Почему нельзя строить ML dataset напрямую из API-ответа:

1. **Воспроизводимость.** Если парсер признаков изменится (например, исправлена ошибка в формуле Elo), нужно пересчитать Feature Data из Normalized Data без повторного похода в API (экономия квоты + скорость).
2. **Аудит.** Raw Data хранит источник и время получения каждой записи — можно всегда объяснить, откуда взялось конкретное число.
3. **Устойчивость к изменению API.** Если OpenDota поменяет формат ответа, меняется только слой Raw→Normalized, а Feature/Dataset код не трогается.
4. **Историческая правильность snapshot'а.** team_rating в OpenDota — это текущий снэпшот, не история. Чтобы восстановить "какой был Elo команды A на 2023-05-01", необходимо иметь Normalized-таблицу всех матчей и пересчитать рейтинг walk-forward самим — то есть Raw/Normalized обязаны существовать отдельно от готовых агрегатов стороннего сервиса.

Эта слоистая схема будет детализирована в `docs/database-design.md` на Phase 4.
