# ADR-003: Собственный walk-forward Elo вместо снэпшота OpenDota

## Статус
Принято (2026-08-24, Phase 3), формализовано как компонент `RatingEngine` в Phase 4

## Context

Team strength — ключевая группа признаков. OpenDota уже считает Elo-рейтинг
команд (`team_rating`, K=32, база 1000 — `VERIFIED` из исходников
`odota/core`), но это ТЕКУЩИЙ снэпшот без истории (см. полный разбор —
`docs/data-leakage.md`).

## Decision

Реализовать собственный компонент `RatingEngine`, пересчитывающий Elo
walk-forward по всей истории матчей, с точным контролем pre-match/post-match
состояния на любую историческую дату. Формула идентична OpenDota (K=32, база
1000) как отправная точка, с возможностью экспериментировать (decay,
adaptive K) без зависимости от чужого сервиса.

## Alternatives

1. **Использовать `team_rating` OpenDota "как есть"** — отклонено: снэпшот,
   не история, использование для исторических матчей = прямая утечка данных
   из будущего (см. `docs/data-leakage.md`, раздел Elo).
2. **Использовать несколько готовых рейтингов одновременно (OpenDota +
   STRATZ)** — отклонено для V1: та же проблема снэпшота у обоих источников,
   плюс лишняя зависимость без выгоды до появления собственного
   walk-forward расчёта.
3. **Glicko-2 вместо Elo** — не отклонено, а отложено: Glicko-2 учитывает
   неопределённость рейтинга (полезно для новых команд/составов), но
   усложняет реализацию. Решение — оставить как кандидата для эмпирического
   сравнения в Phase 8 (Feature Set 0 experiment), не постулировать заранее.

## Why

Подробное обоснование каждого пункта — уже зафиксировано в
`docs/data-leakage.md` (historical state, update timestamp, K-factor,
инициализация, decay, opponent strength). Работоспособность механизма
подтверждена прототипом `scripts/elo_prototype.py`:
`assert_leakage_safe()` независимо пересчитывает рейтинг только по более
ранним матчам и сверяет с pipeline-значением — прогон подтвердил отсутствие
утечки.

## Consequences

- `RatingEngine` — чистый компонент без I/O (принимает поток матчей в
  хронологическом порядке, отдаёт pre/post-match рейтинги), что делает его
  тривиально тестируемым и переиспользуемым и в training pipeline, и в
  backtesting, и в live-инференсе (см. `docs/architecture.md`,
  `docs/backtesting.md`).
- **Жёсткое правило API компонента**: метод, возвращающий рейтинг для
  прогноза, обязан называться и документироваться так, чтобы разработчик не
  мог случайно передать пост-матчевое значение (`get_pre_match_rating(team_id,
  as_of=...)`, не `get_current_rating(team_id)`).
- Требует хранить рейтинг как append-only лог событий
  (`team_ratings(team_id, match_id, rating_before, rating_after)`), а не
  мутируемую таблицу "текущее значение" — см. `docs/database-design.md`.
- Открытый вопрос (сознательно не решается сейчас, см. `docs/data-leakage.md`):
  затухание/частичный сброс Elo при смене состава — предмет Phase 7-8
  эксперимента (Feature Set 0 vs 2).
