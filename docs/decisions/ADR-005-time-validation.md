# ADR-005: Walk-forward time-based validation, без random split

## Статус
Принято (2026-08-24, Phase 4). Точные даты границ — открыты до `REQUIRES LIVE
VERIFICATION` (см. `docs/research-summary.md`, п.5/13).

## Context

Задание категорически запрещает `train_test_split` со случайным
перемешиванием — из-за характера признаков (Elo, форма, ростер — все
последовательны во времени, случайное перемешивание means тренировка на
"будущих" рейтингах, посчитанных с учётом матчей, которые в тестовой выборке
должны быть ещё не сыгранными). Historical depth пока не подтверждена live
(единственное реальное ограничение, влияющее на выбор конкретной схемы).

## Decision

- **Split — исключительно по времени**, без перемешивания.
- Финальная модель оценивается через **walk-forward (rolling-origin)
  backtesting**, а не единственный фиксированный train/val/test срез:
  система идёт по матчам в хронологическом порядке, на каждом шаге признаки
  строятся только из данных до `start_time` текущего матча (см.
  `docs/backtesting.md`).
- Границы периодов задаются конфигурацией
  (`TRAIN_START`, `VALIDATION_START`, `TEST_START`,
  `DATA_START_DATE`/`DATA_END_DATE`/`MIN_MATCH_DATE`), а не хардкодятся —
  см. `docs/architecture.md`, раздел Configuration.

## Alternatives

1. **Единственный фиксированный train/val/test split по датам** (например,
   train=2022-2024, val=2025, test=2026, как предложено в примере из
   исходного задания) — не отклонено полностью, а понижено до **режима
   "quick check"**: полезно для быстрой итерации при разработке pipeline
   (быстрее одного backtest-прогона), но недостаточно для финальной оценки
   — даёт всего одну test-точку, не показывает стабильность качества модели
   по времени (например, деградацию сразу после патча).
2. **K-fold cross-validation (даже time-series-aware, blocked CV)** —
   отклонено как основной метод: k-fold по своей природе усредняет по
   нескольким фолдам, что смазывает главный вопрос "деградирует ли модель
   со временем" — а именно это нужно знать для production-системы,
   переобучаемой периодически.
3. **Random train_test_split** — отклонено категорически, прямое требование
   задания и логическое следствие природы признаков (Elo/форма/ростер
   тавтологически последовательны во времени).

## Why

Walk-forward backtesting — единственная схема, которая ЧЕСТНО имитирует
режим работы production-системы: на каждый момент времени модель видит
только прошлое (см. критический принцип задания: "если остановить время
перед началом матча, могла ли система знать эту информацию?"). Дополнительно
даёт много test-точек вместо одной — можно оценить не только среднее
качество, но и его стабильность/деградацию по времени (важно для
мониторинга дрифта, Phase 12).

## Consequences

- Backtesting дороже вычислительно, чем один train/test прогон (нужно
  переобучать модель на растущем окне много раз, либо использовать
  экспандирующееся/скользящее окно с фиксированным шагом переобучения,
  не "на каждый отдельный матч") — конкретная частота переобучения внутри
  backtest — решение Phase 8, не блокирует архитектуру.
- Все временные признаки (Elo, form, roster) обязаны поддерживать
  "пересчитать состояние на дату X", что уже заложено в `RatingEngine`
  (ADR-003) и требует аналогичного дизайна для остальных stateful-признаков
  (см. `docs/data-pipeline.md`, `docs/ml-architecture.md`).
- Конфигурация периодов через параметры, а не хардкод — прямое следствие
  того, что точная историческая глубина ещё не подтверждена
  (`REQUIRES LIVE VERIFICATION`). Когда `scripts/verify_data_source.py`
  будет прогнан, значения параметров обновляются в конфиге без изменения
  архитектуры или кода backtesting engine.
