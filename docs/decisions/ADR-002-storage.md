# ADR-002: Хранилище — PostgreSQL (JSONB для raw-слоя), без object storage в MVP

## Статус
Принято (2026-08-24, Phase 4)

## Context

Нужно решить, где хранить (а) сырые ответы источников данных (Raw Data,
см. `docs/data-feasibility.md` Phase 2.3) и (б) нормализованные/производные
данные. Варианты для raw-слоя: PostgreSQL JSONB, файловая система, object
storage (S3-совместимое/MinIO).

## Decision

Единая **PostgreSQL** база для всех слоёв (Raw / Normalized / Feature /
Dataset / Model Registry / Predictions), с raw-ответами источников,
хранимыми в колонке `JSONB` таблицы `raw_responses` (не в отдельном object
storage). Подробная схема — `docs/database-design.md`.

## Alternatives

1. **Файловая система (плоские JSON-файлы, как в `odota/core/json/` для
   тестовых фикстур)** — отклонено как основное хранилище MVP: неудобно
   запрашивать ("покажи все raw-ответы за период X"), нет транзакционности,
   нет built-in индексов.
2. **Object storage (S3/MinIO) сразу в MVP** — отклонено для MVP: лишняя
   инфраструктурная сущность на этапе, когда объём raw-данных для
   MVP-периода (ограниченный набор про-матчей, не миллионы записей) не
   создаёт давления на PostgreSQL. Задание прямо предупреждает не добавлять
   инфраструктуру ради красоты.
3. **PostgreSQL JSONB (выбрано)** — один движок для всего, транзакционность
   между raw-записью и ingestion-чекпоинтом, `JSONB` поддерживает индексацию
   (GIN) и частичные запросы без полноценной колоночной схемы.

## Why

- MVP-объём (про-матчи одной экосистемы за разумный период, не десятки
  миллионов записей публичных матчей) не требует отдельного object storage —
  PostgreSQL комфортно держит JSONB-блобы такого масштаба.
- Один движок = меньше операционной сложности (не нужно поднимать/бэкапить
  MinIO отдельно от Postgres на этапе, когда команда — по сути, один
  разработчик/исследователь).
- Транзакции: запись raw-ответа и обновление `ingestion_runs` checkpoint
  можно сделать атомарно в одной БД — сложнее гарантировать при разделении
  file storage + отдельная БД для метаданных.

## Consequences

- **Явно предусмотрен путь миграции**: `raw_responses.response_body JSONB`
  инкапсулировано за repository-слоем (`src/repositories/`, см.
  `docs/architecture.md`), так что переход на "JSONB как индекс + реальный
  blob в S3" в будущем требует изменений только в одном модуле, не во всём
  проекте.
- При росте объёма (например, если проект вырастет от pro-матчей до
  public matches) миграция на object storage потребуется — это осознанный
  технический долг, а не забытая проблема.
- Нет встроенного версионирования сырых blob'ов, как в S3 — при
  необходимости "истории изменений одного и того же raw-ответа" нужно
  полагаться на `(source, endpoint, request_params, fetched_at)` как
  составной ключ (каждый повторный fetch — новая строка, не перезапись).
